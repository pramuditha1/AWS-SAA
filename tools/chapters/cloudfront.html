CloudFront and Global Accelerator — make it closer (two different tools)

Must-knowDomain 3 · edge, cache, static IPs

CloudFront is AWS’s CDN for HTTP and HTTPS. It caches content at edge locations so users download from a nearby POP. Global Accelerator is a different product: two static anycast IPs that pull TCP or UDP onto the AWS backbone. Both help “users around the world.” They answer different exam stems.

Start here — the W questions

Why

A single Region is far from half the planet. Fetching every image from that Region is slow and expensive. You also want a front door that can hide a private S3 bucket and stop some attacks before they reach your origin.

What

CloudFront is a content delivery network: cacheable HTTP(S) at the edge, optional signed URLs, WAF, and edge code. Global Accelerator is a network accelerator: static anycast IPs, any TCP/UDP port you map, no HTTP cache.

Where

Both are global edge services. CloudFront POPs and Regional edge caches sit worldwide. Your origin (S3, ALB, custom HTTP) usually lives in a Region. Global Accelerator endpoints are Regional ALBs, NLBs, or Elastic IPs.

Which pieces matter

Distribution · origin · cache behavior · OAC · signed URL/cookie · ACM in us-east-1 · CloudFront Functions vs Lambda@Edge · Global Accelerator anycast IPs. Those cover almost every SAA edge question.

Core knowledge (beginner foundations)

Cache hit vs miss in one breath

A viewer asks CloudFront for an object. If a nearby edge already has a fresh copy (cache hit), CloudFront returns it without touching your origin. If not (cache miss), CloudFront fetches from the origin, stores a copy (within TTL rules), and returns it. DNS does not do this — CloudFront does.

Distribution — your CloudFront “site” configuration: origins, behaviors, certificates, and price class.

Origin — where CloudFront gets content on a miss: S3 (REST), ALB, EC2, API Gateway, MediaStore/MediaPackage, or a custom HTTP server.

Cache behavior — path rules such as /images/* → S3 with a long TTL, /api/* → ALB with little or no cache.

TTL — how long an object may stay cached. Versioned filenames (app.a1b2c3.js) beat emergency invalidations for static assets.

AWS describes viewer → edge → (on miss) origin → cache → viewer. The Mermaid below follows that story.

OAC — keep the S3 bucket private

Origin Access Control (OAC) lets CloudFront sign requests to S3. The bucket policy allows s3:GetObject only from that distribution. Block Public Access stays on. Guessing the S3 URL fails; using the distribution works (unless signed-URL checks fail).

Origin Access Identity (OAI) is the older pattern. Prefer OAC on new designs — it supports SSE-KMS objects and more Regions. Do not use a public S3 website endpoint and call it locked down; use the S3 REST origin + OAC.

Remember “Users must not open the bucket directly” → OAC + bucket policy + Block Public Access. “Only paying users may download” → CloudFront signed URLs or cookies, still with OAC.

HTTPS certificates at the edge

For a custom domain on CloudFront, the ACM certificate must be in us-east-1 (or imported there). Origin HTTPS to an ALB uses a certificate in the ALB’s Region. Route 53 alias records point the apex and www at the distribution.

Global Accelerator — static IPs, no cache

Global Accelerator gives you two static anycast IPv4 addresses. Clients keep those IPs even if you move backends between Regions. Packets enter a nearby edge and travel the AWS backbone to an endpoint group (ALB, NLB, EIP). It does not cache HTTP and does not replace CloudFront for websites.

Use case 1 — static site with a private bucket

Need: Global HTTPS site from S3; nobody opens the bucket URL directly.

Design: CloudFront + OAC + Block Public Access. ACM cert in us-east-1. Route 53 alias → distribution. Optional WAF on CloudFront.

flowchart LR user[User] --> r53[Route53_alias] r53 --> cf[CloudFront] cf --> oac[OAC] oac --> s3[Private_S3]

Use case 2 — paid downloads

Need: Only customers who paid may fetch large files; still use the CDN.

Design: CloudFront signed URLs (one object) or signed cookies (many objects / HLS). Keep OAC so a stolen S3 URL still fails.

Use case 3 — game server with firewall allowlists

Need: Custom TCP, partners allowlist fixed IPs, failover between Regions.

Design: Global Accelerator → NLB/EIP endpoint groups with health checks. Not CloudFront.

Case study 1 — OAC and apex

Stem

You want example.com over HTTPS, content in S3, users must not read the bucket directly, caching worldwide.

A — wrong Public S3 website endpoint and a CNAME at the apex. Apex CNAME is invalid; bucket is public.
B — correct CloudFront + OAC + private bucket policy. Route 53 alias to CloudFront. ACM cert in us-east-1.
C — wrong Global Accelerator in front of the S3 website endpoint. GA does not cache S3 websites.
D — wrong Paste CloudFront POP IPs into apex A records. Those IPs change.

Case study 2 — CloudFront vs Global Accelerator

Stem

A VoIP appliance must dial fixed IPs. Traffic is UDP. Backends are NLBs in two Regions; unhealthy Region must drop out.

A — wrong CloudFront. Wrong protocol story; no static anycast product for UDP apps.
B — correct Global Accelerator with NLB endpoint groups and health checks.
C — wrong Route 53 latency alone with changing NLB DNS names — partners insisted on fixed IPs.
D — wrong OAC on the NLB. OAC is for S3 origins.

Case study 3 — Functions vs Lambda@Edge

Stem

At viewer request, rewrite /blog to /blog/index.html for millions of requests with minimal latency. No AWS API calls.

A — correct CloudFront Functions on viewer-request.
B — wrong Lambda@Edge that queries DynamoDB — heavier than needed.
C — wrong Regional Lambda behind API Gateway as the only “edge.”
D — wrong Global Accelerator port override.

Tricky points (still explained simply)

CloudFront is not Global Accelerator. Website/cache → CloudFront. Static IP + non-HTTP → Global Accelerator.

OAC ≠ ALB lock-down. For ALB origins, use security groups, a custom header secret, and/or WAF so clients cannot bypass CloudFront.

S3 presigned URL ≠ CloudFront signed URL. With CloudFront in front of a private bucket, prefer CloudFront signed URLs/cookies so auth and cache stay at the edge.

WAF on CloudFront inspects HTTP at the POP — preferred for a global site. Shield Standard already covers CloudFront.
