Migration and disaster recovery — move workloads, survive Regions

Must-knowDomain 2 · RPO/RTO, DMS, MGN, 7 Rs

Migration is how you get onto AWS. Disaster recovery is how you stay alive when a Region or AZ fails. The exam loves two numbers — RPO (how much data you may lose) and RTO (how long you may be down) — and the matching pattern.

Start here — the W questions

Why

Datacenters age out. Databases must move with little downtime. Backups sitting in one Region are not a DR plan if that Region is dark.

What

DR strategies (backup/restore → pilot light → warm standby → multi-site). DMS moves databases. MGN rehosts servers. DataSync / Snow / Transfer Family move files. AWS Backup centralizes backups. The 7 Rs name how you modernize.

Where

DR usually spans Regions. Multi-AZ is inside one Region (high availability, not full Regional DR). Migration tools run in a Region and reach on-premises over VPN/DX or via shipped appliances.

Which pieces matter

RPO/RTO ladder · DMS + SCT · MGN · DataSync vs Snow · AWS Backup · Route 53 failover. Those cover almost every migration/DR stem.

Core knowledge (beginner foundations)

RPO and RTO in one breath

RPO (recovery point objective) — how stale can the recovered data be? (minutes of lost writes vs hours). RTO (recovery time objective) — how long until users work again? Cheaper DR means larger RPO/RTO. Near-zero needs active-active and cost.

StrategyIn plain EnglishTypical RPO/RTO
Backup and restoreStore backups; build when disaster hitsHours / hours
Pilot lightCore data tier ready; scale apps on eventMinutes / tens of minutes
Warm standbySmall full stack always on; scale outSeconds–minutes / minutes
Multi-site active/activeFull prod in two+ RegionsNear zero / near zero

DMS (Database Migration Service) — continuous replication with full load + CDC; source stays up. SCT converts schemas for heterogeneous moves (Oracle → PostgreSQL).

MGN (Application Migration Service) — block-level replication of servers for lift-and-shift (rehost).

DataSync — online file sync/migrate to S3/EFS/FSx. Snow — ship petabytes offline. Storage Gateway — ongoing hybrid access (not one-shot migrate).

The 7 Rs (migration strategy names)

Exam stems often paraphrase: Rehost (lift-and-shift, MGN), Replatform (managed DB, little code change), Refactor/re-architect (serverless/microservices), Repurchase (SaaS), Retire, Retain, Relocate (VMware Cloud on AWS). Match the verb to the tool.

Remember Multi-AZ RDS ≠ cross-Region DR. For Regional failure you need cross-Region replicas/snapshots, Aurora Global, DynamoDB Global Tables, or an explicit DR stack.

Use case 1 — database with minimal downtime

Need: Oracle on-premises → Aurora PostgreSQL; keep source writable during cutover.

Design: SCT for schema, DMS full load + CDC, cut over when lag is tiny.

Use case 2 — cheap Regional DR

Need: RTO of hours is OK; minimize cost.

Design: Backup and restore: AWS Backup / snapshots copied cross-Region; rebuild from AMIs and IaC when needed.

Use case 3 — large filesystem migrate

Need: 80 TB NAS → S3; network is too slow for the deadline.

Design: Snowball/Snowball Edge (or Snowmobile at extreme scale). Use DataSync when the pipe is good enough for online transfer.

Case study 1 — RTO minutes

Stem

RPO of seconds and RTO of a few minutes. Budget allows a small always-on copy in a second Region.

A — wrong Backup and restore only — RTO is hours.
B — wrong Pilot light with cold app tier and long AMI launch if the stem’s RTO is a few minutes and they already fund a running mini-stack.
C — correct Warm standby: functional scaled-down environment, scale out + Route 53 failover on disaster.
D — wrong Multi-AZ in one Region only — does not cover Regional failure.

Case study 2 — heterogeneous DB

Stem

SQL Server on-premises must become Aurora MySQL with almost no cutover window.

A — wrong DMS alone without schema conversion planning — engines differ.
B — correct SCT to convert schema + DMS full load and CDC, then cut over.
C — wrong MGN for the database host only — still SQL Server, not Aurora MySQL.
D — wrong Snowball with a weekend outage when they forbade downtime.

Case study 3 — rehost servers

Stem

Hundreds of VMs must move with minimal change; continuous block replication until cutover.

A — correct AWS Application Migration Service (MGN).
B — wrong DMS — databases, not general VMs.
C — wrong Only AMI import once with weeks of freeze.
D — wrong AppFlow.

Tricky points (still explained simply)

HA ≠ DR. Multi-AZ protects against AZ failure. Regional DR needs another Region.

Replication lag is RPO. Async cross-Region replicas can lose the last few seconds/minutes of writes.

DataSync vs Storage Gateway. DataSync migrates/syncs. Gateway keeps a hybrid file/volume/tape presence long term.

AWS Backup orchestrates backups across services; it is not by itself a running standby.

Light touch on the exam Exact Snow device SKUs, DMS tuning knobs, CloudEndure legacy naming (use MGN).
