DynamoDB — a fast key-value database you do not patch

Must-knowDomains 2 & 3 · Resilient · Performance

DynamoDB is AWS’s managed NoSQL database. You store items (rows) in a table, look them up by a key, and AWS keeps the data Multi-AZ and highly available. On the exam it is the default when you want single-digit millisecond reads, unpredictable traffic, and almost no database operations. API Gateway often sits in front as the HTTPS door for mobile or partner apps.

Start here — the W questions

Why

Relational databases are great for joins and complex queries, but they make you size instances, plan capacity, and babysit failover. Many apps only need “get this user,” “list this user’s orders,” or “write a session.” Those patterns want a simple, automatic, pay-per-use store.

What

Amazon DynamoDB is a fully managed key-value and document database. There is no SQL join engine and no server for you to patch. You design a primary key, choose a capacity mode, and call Get/Put/Query APIs (often from Lambda).

Where

A table lives in one Region. Inside that Region, AWS stores copies across Availability Zones automatically — there is no Multi-AZ checkbox. Global Tables copy the same table to other Regions for active-active writes. DAX (a cache) sits in your VPC next to your app.

Which pieces matter

Partition key · sort key · GSI/LSI · on-demand vs provisioned · eventually vs strongly consistent reads · Global Tables · DAX · Streams/TTL. API Gateway (REST vs HTTP, 29-second timeout) shows up when DynamoDB is the backend of a public API.

Core knowledge (beginner foundations)

Items, attributes, and keys

An item is one record (like a row). An attribute is a field on that item. Every table needs a primary key. With only a partition key (also called hash key), each key value is unique — for example one profile per userId. With a partition key plus a sort key (range key), many items share the same partition — for example all orders for userId, sorted by orderDate.

Partition — DynamoDB hashes the partition key and places items on a storage partition. Throughput scales by adding partitions. If almost all traffic hits one key (one popular product ID), that partition gets “hot” and throttles even when the table has spare capacity overall.

Query vs Scan — A Query uses the key (or an index key) and is cheap. A Scan reads the whole table (or index) and filters afterward — slow and expensive at scale. Exam stems about exploding bills almost always mean “they are scanning.”

Consistency — By default, reads are eventually consistent (usually catch up within a second, cheaper). A strongly consistent read always returns the latest write, costs more RCU, and works on the base table (and LSI) — not on a GSI.

Capacity: on-demand vs provisioned

On-demand bills per request. Traffic can spike without you pre-setting RCU/WCU. Use it when load is unknown, spiky, or “new product — we will not tune capacity.”

Provisioned asks you for read capacity units (RCU) and write capacity units (WCU), often with auto scaling. One RCU ≈ one strongly consistent 4 KB read per second (or two eventually consistent). One WCU ≈ one 1 KB write per second. Use provisioned when traffic is steady and you can predict (or discount) capacity.

On-demand is a billing mode, not a slower engine. Do not pick provisioned “for performance” when the stem is about unpredictable load.

Remember Unpredictable / spiky / least ops → on-demand. Smooth known load → provisioned (+ auto scaling). Never “provision huge WCU to fix a hot partition” — fix the key design.

Secondary indexes — when the first key is not enough

IndexIn plain EnglishExam rule
LSISame partition key, different sort keyCreate only with the table; can be strongly consistent; shares table capacity
GSINew partition key (and optional sort)Can add later; eventually consistent only; own capacity (or on-demand)

Need “look up by email” when the table is keyed by userId? That is a GSI on email. Need “same user’s items sorted by status instead of date,” decided at create time? That can be an LSI. Asking for a strongly consistent read on a GSI is always wrong — redesign the primary key or read the base table.

Global Tables, DAX, Streams, TTL

Global Tables — multi-Region active-active replication. Write in Tokyo and Ireland; each Region has a local copy. Conflicts use last-writer-wins per item. This is not Aurora Global (one writer Region). Pick Global Tables when the stem wants local writes in more than one Region or regional isolation with active-active.

DAX — DynamoDB Accelerator, a write-through cache in your VPC for microsecond repeated reads of the same keys. Prefer DAX when the stem says microsecond / DynamoDB-compatible cache with least app change. ElastiCache works too but needs more application code.

Streams — ordered change log (~24 hours). Lambda can react to inserts/updates. Not a long-term audit vault (use PITR / AWS Backup).

TTL — an epoch attribute; DynamoDB eventually deletes expired items (sessions, temp links). Not a precise legal-hold clock.

API Gateway in one page (when DynamoDB is the backend)

API Gateway is the managed HTTPS front door. A client hits a stage URL → auth → integration (often Lambda → DynamoDB, or a direct AWS service proxy).

Hard limit: HTTP/REST integration timeout ≈ 29 seconds. Even if Lambda can run 15 minutes, a synchronous API Gateway call dies at ~29 s. Long work must return 202 and finish via SQS or Step Functions.

Use case 1 — mobile game inventory

Need: Spiky launch traffic, look up by player ID (always fresh) and by score (leaderboard can be slightly stale), hot catalog keys read constantly.

Design: On-demand table keyed by playerId. Strongly consistent Get on the base table for the bag. GSI on score for the leaderboard. DAX for catalog keys.

Use case 2 — active-active preferences worldwide

Need: Users in the US and EU write preferences locally; a Region outage must not block writes; last-writer-wins is OK.

Design: DynamoDB Global Tables in both Regions. App writes to the local endpoint.

Use case 3 — API that starts a long job

Need: Partners POST a video; processing takes minutes; Cognito JWT already exists; some partners need daily request caps.

Design: REST API + Cognito authorizer + usage plans. Lambda returns 202 and starts Step Functions/SQS. Never hold the HTTPS call for the whole render.

Case study 1 — on-demand, GSI, DAX

Stem

A mobile game stores inventories in DynamoDB. Traffic is quiet at night and can jump 100× at launch. Leaderboards query by score; bag opens need the latest inventory. A few catalog keys are read constantly and must be as fast as DynamoDB allows. Least ops, cost-aware, highly available?

A — wrong Huge fixed provisioned RCU/WCU, add an LSI on score a week later, Memcached on EC2.
B — wrong On-demand + GSI on score + strongly consistent GSI reads for bag and leaderboard; no cache.
C — correct On-demand, PK = playerId, strongly consistent Get on base table for the bag, GSI on score for leaderboard, DAX for catalog.
D — wrong Move to RDS Multi-AZ and cache inventory in CloudFront for 24 hours.

A cannot add an LSI later and adds servers. B invents strongly consistent GSI reads. D is the wrong database and a stale CDN. C matches traffic shape, consistency rules, and the microsecond hint.

Case study 2 — Global Tables

Stem

Preferences must be writable in us-east-1 and eu-west-1 with low local latency. Region failure must not block writes. Last-writer-wins is fine. Data is already in DynamoDB. Least ops?

A — wrong Aurora Global + nightly DMS from DynamoDB.
B — correct DynamoDB Global Tables; app writes to the local Regional endpoint.
C — wrong Custom Streams + Lambda replicator and manual failover flags.
D — wrong On-demand backup every 15 minutes and restore in the other Region.

B is the managed active-active feature. A changes engines. C reinvented Global Tables. D is DR with poor RPO/RTO, not active-active.

Case study 3 — the 29-second wall

Stem

Partners submit videos over HTTPS. Processing takes 3–8 minutes. JWTs come from Cognito. Some partners need 10 requests/day with rotatable keys. Backend is already Lambda + S3.

A — wrong HTTP API, JWT auth, timeout set to 10 minutes, usage plans on HTTP API.
B — wrong ALB → Lambda, give each partner an IAM user access key.
C — correct REST API + Cognito + API keys/usage plans; Lambda starts the job and returns 202; client polls or gets a callback.
D — wrong WebSocket held open for 8 minutes while one sync Lambda runs to completion.

Integration timeout stays ~29 s; HTTP API lacks REST usage plans; IAM users for partners are ops hell. Async accept is the design.

Tricky points (still explained simply)

GSI reads are eventually consistent only. Strong consistency → base table or a better primary key.

LSI vs GSI. LSI = same partition key, create-time only. GSI = new partition key, add later, own capacity.

On-demand vs provisioned is about predictability, not raw speed.

Hot partitions are a key-design problem. Adaptive capacity helps briefly; it does not invent infinite writes on one key.

DAX vs ElastiCache vs CloudFront. DAX = DynamoDB API, microseconds. Redis = app-shaped cache. CloudFront = edge HTTP.

Streams ≈ 24 hours for change-driven compute — not your compliance archive.

API keys ≠ users. Auth is Cognito/IAM/Lambda authorizer; keys are metering.
