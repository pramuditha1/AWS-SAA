Messaging — queues, topics, buses, and streams

Must-knowDomains 2 & 3 · Resilient · Performance

Messaging lets one part of your system talk to another without both being online at the same second. On the SAA exam you match a human need — buffer work, fan out news, replay a day of clicks, land data in S3, keep JMS, route SaaS events — to the AWS product whose rules already fit.

Start here — the W questions

Why

If a web server calls a worker directly, a spike or a crashed worker breaks the user request. Decoupling with a queue or bus absorbs the spike, lets workers die and retry, and lets new subscribers appear without rewriting the producer.

What

AWS messaging is a family: SQS (queue), SNS (pub/sub topic), EventBridge (event bus with rules), Kinesis Data Streams (replayable log), Firehose (delivery into S3/analytics stores), and Amazon MQ (managed ActiveMQ/RabbitMQ for existing apps).

Where

These services are Regional and Multi-AZ under the hood. You talk to Regional endpoints. Cross-account and SaaS partners usually meet you on an EventBridge bus. MQ brokers sit in your VPC subnets.

Which pieces matter

SQS Standard vs FIFO · visibility timeout · DLQ · SNS fan-out · EventBridge content rules · Kinesis shards + replay · Firehose destinations · Amazon MQ for JMS. Those ideas cover almost every messaging stem.

Core knowledge (beginner foundations)

Pick the conversation shape first

Queue — one unit of work, competing consumers; whoever takes the message owns it (SQS). Fan-out — many independent subscribers each get a copy (SNS or EventBridge). Stream — a durable ordered log many apps can read and rewind (Kinesis Data Streams). Delivery pipe — land batches in S3/Redshift/OpenSearch with least ops (Firehose). Old broker protocols — JMS/AMQP/MQTT to ActiveMQ or RabbitMQ (Amazon MQ).

Cost-effective and least ops usually means the managed AWS-native service. MQ exists because “rewrite every JMS client before Friday” is not least ops.

SQS — a work inbox

A producer sends a message to a queue URL. A consumer calls ReceiveMessage. SQS then hides the message for the visibility timeout (default 30 seconds, max 12 hours). If the consumer deletes it in time, work is done. If the consumer crashes, the message reappears for someone else. Queue depth is a classic Auto Scaling metric.

Standard queues — nearly unlimited throughput, at-least-once delivery, best-effort order. Duplicates can happen; make the worker idempotent (natural key, DynamoDB condition).

FIFO queues — order per message group ID, and exactly-once processing inside a deduplication window. Group account-123 keeps that account’s messages ordered; other groups run in parallel. One group ID for the whole company invents a single-threaded bottleneck.

Max body size is 256 KB. Bigger payloads use the Extended Client (body in S3, pointer on the queue). A dead-letter queue (DLQ) gets messages after too many receives without a delete — alarm on DLQ depth. Retention is 1 minute to 14 days (default 4 days), not a long archive.

SNS — one publish, many subscribers

Publish to a topic. SNS pushes to each subscription: SQS, Lambda, HTTPS, email, SMS, mobile push, Firehose. That is fan-out: order-placed becomes “email customer,” “update search,” and “notify billing” without the order service knowing those three.

The durable exam pattern is SNS → SQS → worker (each team gets its own queue and DLQ), not SNS → one EC2 HTTPS endpoint. Filter policies let a subscriber ignore messages it does not care about. FIFO topics pair only with FIFO queues when order + fan-out both appear.

Where SNS messages actually get lost

SNS has no servers for you to add. It scales by itself, so on the exam "provision more SNS servers" is always wrong. It does have a publish quota per account per Region, and it is a soft quota. If you hit it, the publisher gets a throttling error back from Publish, so you would see errors where the message is sent.

SNS calls a Lambda subscriber with an asynchronous invoke: it hands over the event and moves on. Lambda then needs a free concurrent execution, which is one running copy of the function. The account default is 1,000 per Region. Above that, Lambda throttles. It keeps throttled async events in its own queue and retries them for up to 6 hours. After that it discards them, unless you configured an on-failure destination or DLQ.

When SNS cannot deliver to a subscriber at all, it retries using a delivery policy. For AWS endpoints (Lambda, SQS, Firehose) that is about 100,000 attempts over 23 days. For HTTP/S, email, and SMS it is 50 attempts over 6 hours. After that SNS drops the message, unless the subscription has its own SQS dead-letter queue.

Follows Lambda async error handling, Lambda concurrency, and SNS delivery retries.

Concurrency math: concurrency = requests per second × average duration in seconds. At 100 rps × 0.5 s you need 50, which is fine. At 5,000 rps × 0.5 s you need 2,500, over the 1,000 default. The fix is to raise the Lambda account concurrency quota through Service Quotas or AWS Support. To make sure nothing is lost during spikes, also add a DLQ or on-failure destination, or put SQS between SNS and Lambda.

EventBridge — a smart event bus

EventBridge routes events with content-based rules (match on source, detail-type, fields inside JSON detail). Sources include AWS services (default bus), your apps (custom bus), and SaaS partner integrations. Targets include Lambda, SQS, SNS, Step Functions, Kinesis, API destinations, and more. Archive/replay and Scheduler (cron/rate) sit beside the bus.

SNS vs EventBridge: both can fan out. EventBridge wins for SaaS partners, rich payload matching, archive/replay, and “corporate event bus.” SNS wins for simple pub/sub to SQS/Lambda/SMS/email.

Kinesis Data Streams vs Firehose

Kinesis Data Streams — a durable log split into shards. Producers put records (up to 1 MB). Multiple consumers can each read the same data at their own pace. You can replay within retention (24 hours default, extendable). Enhanced fan-out gives a consumer its own throughput pipe. Use for clickstream, many analytics apps, “reprocess yesterday after a bug fix.”

Firehose (Amazon Data Firehose) — a managed pipe that buffers and delivers to S3, Redshift, OpenSearch, Splunk, HTTP, with optional Lambda transform. You do not build a custom batcher. You do not replay to five custom apps. Near-real-time (buffer interval), not sub-second per record.

Amazon MQ — keep the old protocol

Managed ActiveMQ or RabbitMQ speaking JMS, AMQP, MQTT, and friends. Multi-AZ active/standby (ActiveMQ) or cluster (RabbitMQ). Use when the stem says migrate with minimal code change or “vendor requires RabbitMQ.” Green-field Lambda microservices should prefer SQS/SNS/EventBridge.

Use case 1 — website → workers

Need: Web tier must not wait on image processing; scale workers on backlog; tolerate crashes.

Design: Standard SQS + Auto Scaling or Lambda event source, long polling, DLQ, idempotent worker.

Use case 2 — one event, three teams

Need: Order placed notifies billing, fulfillment, and a lake dump. Billing/fulfillment need per-account order and no duplicates.

Design: SNS FIFO (or EventBridge) → two SQS FIFO queues (group = account ID). Lake path via Firehose/S3 (at-least-once OK). Extended Client if bodies exceed 256 KB.

Use case 3 — telemetry with replay + lake

Need: Fraud app re-reads 48 hours; dashboard must not steal fraud’s read throughput; durable copy in S3 and OpenSearch.

Design: Kinesis Data Streams (retention ≥ 48 h, enhanced fan-out for fraud) + Firehose to S3/OpenSearch.

Case study 1 — fan-out, order, large payload

Stem

Order service must notify billing, fulfillment, and a data lake. Billing and fulfillment need per-account order and no duplicates. Some documents are ~1 MB. Lake can be at-least-once. No self-managed brokers.

A — wrong One Standard SQS; three teams compete; raise message size quota to 1 MB.
B — wrong Single-AZ Amazon MQ so JMS “guarantees order.”
C — correct Fan-out to two SQS FIFO queues (group = account ID) + Extended Client for size; lake via Firehose/S3.
D — wrong One-shard Kinesis “for global order” with three Lambdas.

A fails order, exactly-once, size, and fan-out. B adds a broker in one AZ. D forces global order you did not need. C matches each constraint with managed features.

Case study 2 — Streams + Firehose

Stem

Multi-MB/s telemetry needs (1) a fraud detector that can re-read 48 hours, (2) a dashboard that must not steal fraud’s throughput, (3) S3 + OpenSearch with no custom batcher.

A — wrong Standard SQS with two Lambdas and 14-day retention as the “lake.”
B — wrong Firehose only; fraud polls S3 every five minutes.
C — correct Kinesis Data Streams (≥48 h, enhanced fan-out for fraud) + Firehose to S3 and OpenSearch.
D — wrong EventBridge archive as the only ingest pipe + MQ to OpenSearch.

SQS cannot share one message with two independent readers or rewind after delete. Firehose alone is not a real-time dual-consumer log. C is the documented split.

Case study 3 — JMS today, SaaS tomorrow

Stem

On-prem app speaks JMS to ActiveMQ; migrate in a month with little code change and Multi-AZ. Also receive SaaS stock events (EventBridge partner) and run Lambda only when detail.type is STOCK_OUT.

A — wrong Rewrite to SQS FIFO this sprint; SaaS POSTs to an ALB; filter in every Lambda.
B — correct Amazon MQ Multi-AZ for JMS; EventBridge partner source + content rule → Lambda.
C — wrong Homegrown JMS→Kinesis agent and SNS email for SaaS.
D — wrong Single-AZ RabbitMQ on EC2; EventBridge only if SaaS speaks AMQP.

B uses MQ and EventBridge for the reasons each exists. A ignores the timeline and the partner integration.

Case study 4 — SNS → Lambda drops messages at peak

Stem

A website sends notifications through SNS to a Lambda function that delivers them to users. Off-season load is ~100 requests/second and works fine. At peak season it is ~5,000 requests/second, and many notifications never reach users. What is the BEST fix?

A — wrong Provision more servers running SNS.
B — correct SNS deliveries to Lambda have crossed the Lambda account concurrency quota. Ask AWS Support to raise it.
C — wrong SNS hit a scalability limit. Ask AWS Support to raise the SNS limit.
D — wrong Provision more servers running Lambda.

A and D fail because both services are serverless, so there are no servers to add. C is the trap. SNS is built to absorb large publish rates. If SNS were throttling, the publisher would get errors on Publish. The stem says messages are published but users never get them, so the problem is on the subscriber side. 50× the traffic means 50× the concurrent Lambda executions, and the default 1,000 per Region runs out. Throttled async events are retried, then dropped.

Tricky points (still explained simply)

Visibility timeout ≠ delay queue. Hide time must cover processing or another worker grabs the same message. Delay is “wait up to 15 minutes before first delivery.”

One queue is not fan-out. Competing consumers share work. Copies for every team need SNS, EventBridge, or a stream.

Standard SQS duplicates are normal. Fix with idempotency, not FIFO, unless the stem asked for order and exactly-once.

256 KB for SQS/SNS bodies on the exam’s memory — use S3 pointers or choose a stream if you needed a stream anyway.

"SNS hit a limit" is usually the trap. When SNS feeds Lambda and messages vanish under load, blame Lambda concurrency (1,000/Region default). Serverless services never take "add servers" as an answer.

Firehose is near-real-time. Sub-second Lambda processing of every record → Streams.

MQ ≠ “SQS with JMS paint.” Different HA, billing, and protocols. First migration step can still be MQ.

Light touch on the exam Exact high-throughput FIFO quota numbers, every Firehose buffer knob, MQ engine version minutiae. Know when to pick the product.
