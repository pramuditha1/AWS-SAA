Lambda and Step Functions — run code without servers, then sequence it

Must-knowDomains 2, 3 & 4 · Resilient · Performance · Cost

Lambda runs your function when an event arrives — upload, API call, queue message — and AWS handles the fleet. Step Functions is the managed flowchart when one function is not enough. On the exam they are the default “least operations” compute, until a time limit or a VPC need forces a different shape.

Start here — the W questions

Why

Patching and scaling a server for a 200 ms handler is waste. You want to pay for the second the code runs, survive Multi-AZ automatically, and wire S3, API Gateway, or SQS without writing a custom worker fleet.

What

AWS Lambda is serverless functions: you provide code (or a container image), memory size, and a timeout. Step Functions is a state machine that calls Lambda (and other AWS services) with retries, waits, choices, and human approvals.

Where

Functions run in a Region, Multi-AZ by default. By default they are not inside your VPC — they reach AWS APIs on the AWS network. Attach a VPC only when you must reach private resources (RDS, ElastiCache, private EC2). Step Functions is also Regional and managed.

Which pieces matter

15-minute max runtime · execution IAM role · sync vs async invoke · VPC attach · reserved vs provisioned concurrency · destinations/DLQ · Standard vs Express Step Functions. Those cover almost every SAA Lambda question.

Core knowledge (beginner foundations)

A function in one breath

You upload a handler. An event arrives. Lambda starts (or reuses) an execution environment — a small MicroVM with your runtime, the memory you chose, and a writable /tmp. Your code runs, returns a result, and you are billed for duration × memory. The first start after idle is a cold start; later invokes on the same environment are warm.

Hard ceiling: maximum runtime is 15 minutes (900 seconds). Raising memory does not raise the time limit. A 40-minute job is Fargate, Batch, Glue, or Step Functions stitching shorter tasks — not one Lambda with a fantasy timeout.

Memory is also CPU. More memory means more CPU and network. CPU-bound functions often finish faster (and sometimes cheaper) at higher memory. Waiting on a slow SQL query is not fixed by memory alone.

Execution role — an IAM role Lambda assumes. It needs permission to write logs and to call whatever the code calls (S3, DynamoDB, Secrets Manager). Callers (S3, EventBridge, another account) need permission to invoke the function (resource-based policy). Environment variables are not a secret store — use Secrets Manager or SSM and cache in global scope.

How invocation works (from AWS docs)

AWS groups invokes into three styles. Retries and failure paths differ, so read the stem for which style you are in.

Follows invocation types in Invoking Lambda functions and Asynchronous invocation.

Synchronous — API Gateway, ALB, Cognito triggers, SDK RequestResponse. Caller waits. API Gateway still stops at ~29 seconds even if the function could run longer.

Asynchronous — S3, SNS, EventBridge, Event invoke type. Lambda retries on error, then can send to an on-failure destination (SQS, SNS, EventBridge, Lambda) or a legacy DLQ. Without that, the failed event can vanish after retries.

Event source mapping — SQS, Kinesis, DynamoDB Streams. A poller batches records into your function. Configure partial-batch failure and the source’s own DLQ — an async function DLQ does not replace that.

IAM role and VPC — two separate decisions

IAM: every function has an execution role. Least privilege: only the APIs and resources it needs. Do not confuse “role can read S3” with “S3 is allowed to invoke this function” — that second part is a resource policy on the function (or the event source configuration).

VPC: attach subnets and security groups only to reach VPC resources. Then the function needs a path out for public AWS APIs if required (NAT or VPC endpoints). If the function only talks to S3 and DynamoDB, do not attach a VPC — simpler, fewer cold-start and IP headaches. “VPC for security by default” is a common wrong instinct on the exam.

Step Functions — Standard vs Express

A state machine says: run this task, wait, choose, map over a list, catch errors, maybe wait for a human taskToken. The compute is still Lambda (or Fargate, Glue, HTTP). Step Functions owns the durable pointer and retries so you do not sleep inside a 15-minute function.

StandardExpress
DurationUp to one yearUp to five minutes
SemanticsExactly-onceAt-least-once
BillingPer state transitionDuration × memory (high volume)

Use case 1 — HTTP API, short work

Need: HTTPS API, ~200 ms CPU, unknown scale, talks only to DynamoDB.

Design: API Gateway + Lambda, no VPC, execution role with DynamoDB permissions.

Use case 2 — long render + short thumbnail

Need: Upload returns quickly; thumbnail in seconds; 12–20 minute render must not fail silently; metadata in Aurora.

Design: API returns 202 after S3 put. S3 → Lambda for thumbnail. Step Functions / Batch / Fargate for the long render. RDS Proxy + reserved concurrency on anything that touches Aurora. Destinations/Catch → SQS + alarm.

Use case 3 — human approval then charge

Need: Validate, wait up to days for an adjuster, charge exactly once; also run a noisy 2-second fraud score at high rate.

Design: Standard workflow for the claim (waitForTaskToken + charge). Express workflow (or child) for fraud enrichment.

Case study 1 — 15 minutes, 29 seconds, Aurora

Stem

Users POST an image over HTTPS. Thumbnail in 1–2 seconds. High-res render takes 12–20 minutes and must not fail silently. Job metadata goes to Aurora. Bursty traffic. Least ops, cost-aware, highly available?

A — wrong One Lambda timeout 20 minutes, sync behind API Gateway, provisioned concurrency 500, image stored only in /tmp.
B — wrong One always-on m5.4xlarge, no Auto Scaling.
C — correct Fast accept (202) + S3; Lambda thumbnail; Step Functions/Batch/Fargate for long render; RDS Proxy + reserved concurrency for Aurora touchers; failure to SQS/alarm.
D — wrong WebSocket open 20 minutes while Express runs a 20-minute Lambda.

A hits three walls (15 min, 29 s, ephemeral disk) and warms a DB stampede. D invents illegal durations. C splits by duration.

Case study 2 — two concurrency knobs

Stem

Checkout API on Lambda has bad p99 after deploys (cold starts); need <200 ms. Analytics Lambda yesterday ate the Regional concurrency pool and checkout got 429s. Checkout uses DynamoDB only; analytics uses RDS.

A — wrong Reserved=10 on checkout; provisioned=1000 on analytics; both in the RDS VPC.
B — correct Provisioned concurrency on checkout alias; reserved concurrency on analytics; checkout stays out of VPC; analytics uses RDS Proxy (and maybe SQS).
C — wrong Move checkout to one Reserved EC2; leave analytics unbounded.
D — wrong Destinations on checkout “to skip the handler and go faster.”

Reserved caps; provisioned warms. A does both backwards and VPC-attaches checkout for no reason. Destinations do not speed sync APIs.

Case study 3 — Standard vs Express

Stem

Insurance flow: validate → wait up to five days for adjuster → charge exactly once. Also 20k/min fraud enrichments that finish in two seconds and are idempotent. One orchestration family, no self-managed workers.

A — wrong One Express workflow that waits five days then charges.
B — wrong One Lambda that polls DynamoDB for approval inside a 15-minute loop.
C — correct Standard workflow for claim + human token + charge; Express (or Express child) for fraud enrichment.
D — wrong Amazon MQ for the adjuster because “Step Functions cannot wait for humans.”

Express cannot run five days and is at-least-once on the charge. C matches both semantic models.

Tricky points (still explained simply)

Four clocks: Lambda 15 minutes · API Gateway ~29 seconds · Express 5 minutes · Standard up to 1 year. Many stems are a duration test.

VPC is not a security default — it is how you reach private resources.

Reserved vs provisioned — safer/isolate/disable vs warmer/faster. You can use both on different functions.

Destinations/DLQs are for async (and mapping failures). A failed sync API already returns the error to the client.

Idempotency matters wherever retries exist: async, Standard SQS, Express, stream bisects.

Scheduler → heavy work: EventBridge Scheduler can start Step Functions/Glue/Batch. Do not schedule a 40-minute job as one Lambda.

Step Functions ≠ EventBridge ≠ SQS. Bus starts work; queue buffers work; Step Functions coordinates steps.
