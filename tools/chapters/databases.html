RDS, Aurora, ElastiCache, and RDS Proxy — managed databases without SSH

Must-knowDomains 2 & 3 · Resilient · Performance

Amazon RDS runs a relational engine for you: backups, patching, and failover without you SSH-ing into MySQL. Aurora is RDS’s cloud-native engine with storage that already copies data across AZs. ElastiCache speeds reads in memory. RDS Proxy pools connections when Lambda opens too many. The exam’s trick is mixing up Multi-AZ, read replicas, and Multi-Region.

Start here — the W questions

Why

Apps need durable structured data, fast reads, and a plan when an AZ fails. Running Postgres yourself on one EC2 box means you own backups, failover, and patches. Managed databases take that toil — if you pick the right feature for HA vs read scale vs another Region.

What

RDS is managed MySQL, PostgreSQL, MariaDB, SQL Server, Oracle (and Aurora variants). Aurora is a compatible engine with a shared storage fabric. ElastiCache is managed Redis or Memcached in front of your database of record. RDS Proxy multiplexes many app connections onto fewer DB connections.

Where

These services run in a Region, inside your VPC (subnet groups). Multi-AZ stays inside one Region. A cross-Region read replica or Aurora Global Database is how you span Regions. Caches and proxies sit near the app tier in the VPC.

Which pieces matter

Multi-AZ vs read replica vs Multi-Region · Aurora storage and reader endpoint · encryption (KMS) · RDS Proxy · Redis vs Memcached · automated backups / PITR. Those distinctions decide most SAA database stems.

Core knowledge (beginner foundations)

RDS in one breath

You choose an engine, instance class, storage, a DB subnet group (two AZs if you want Multi-AZ), and a security group. AWS gives you a DNS endpoint. You do not get SSH. Parameter groups hold engine settings. Automated backups go to S3 during the backup window; point-in-time restore creates a new instance.

Encryption at rest uses KMS. You cannot flip encryption on for an already-running unencrypted RDS instance. The supported path is snapshot → copy snapshot with encryption → restore → cut over.

Encryption in transit is the engine’s SSL/TLS (and parameters that reject plaintext).

When not RDS: key-value at any scale → DynamoDB; graph → Neptune; this chapter assumes the stem already wants SQL or a cache in front of SQL.

Remember Multi-AZ ≠ read scale. Read replica ≠ sync HA standby. Multi-Region ≠ Multi-AZ. If the stem only says “survive AZ failure,” Multi-AZ (or Aurora’s built-in storage HA) is the answer — not a cross-Region replica.

Some engines also offer Multi-AZ DB clusters with readable standbys. If the stem explicitly says that, believe it. If it just says “Multi-AZ,” assume classic: standby is not for reads.

How Aurora storage works (from AWS docs)

Aurora keeps six copies of your data across three AZs. Compute nodes (one writer, optional readers) attach to that volume. An Aurora replica is another compute reader on the same durable storage — not a second slow binlog copy like classic MySQL replication.

flowchart LR writer[Aurora_writer] --> vol[Shared_cluster_volume] reader1[Aurora_reader] --> vol reader2[Aurora_reader] --> vol vol --> az1[Copy_AZ1] vol --> az2[Copy_AZ2] vol --> az3[Copy_AZ3] app[App] --> clusterEP[Cluster_endpoint_writer] app --> readerEP[Reader_endpoint] readerEP --> reader1 readerEP --> reader2

Follows the Aurora storage and endpoint model in Amazon Aurora DB clusters. Open that page for AWS’s official diagrams.

Cluster endpoint — always points at the current writer. Reader endpoint — load-balances across Aurora replicas. Apps must reconnect after failover (DNS changes).

Aurora Serverless v2 — capacity in ACUs that scale with load; good for bursty or intermittent relational work. Steady 24/7 load often stays cheaper on provisioned instances.

Aurora Global Database — managed Multi-Region Aurora with storage-level replication (typical lag under one second). The low-RPO / minutes-RTO Multi-Region answer for Aurora — better than “copy snapshots every hour” when the stem asks for least ops and tight RPO.

Cloning — fast copy-on-write cluster for QA. Backtrack (MySQL-compatible) — rewind the writer in-place for a window; not a substitute for backups.

RDS Proxy — when connections are the outage

Each DB connection costs memory on the writer. Hundreds of Lambda environments that each open a connection can hit max_connections before they hit CPU. RDS Proxy sits between the app and RDS/Aurora, reuses fewer DB connections, can shorten failover pain for the client, and pairs with IAM auth / Secrets Manager so passwords are not in the function code.

Proxy is not a cache, not Multi-AZ, and not encryption. Slow reads → replicas, bigger instance, or ElastiCache — not Proxy.

Lazy loading (cache-aside) — read cache; on miss read RDS then fill cache. Write-through — update cache when you write the DB. TTL expires stale keys. The database of record for orders is still RDS/Aurora/DynamoDB — the cache accelerates; it does not replace durability requirements.

Use case 1 — HA writer in one Region

Need: Survive AZ failure; same connection string; no read-scale story in the stem.

Design: RDS Multi-AZ (or Aurora, which already spreads storage across three AZs). Do not answer with “add a read replica” alone.

flowchart LR app[App] --> ep[RDS_endpoint] ep --> primary[Primary_AZ_a] primary -->|sync| standby[Standby_AZ_b]

Use case 2 — reporting pile-on

Need: Dashboards hammer SELECT; writes must stay healthy.

Design: Read replicas (or Aurora readers) for reporting; keep Multi-AZ for writer HA. Or put hot keys in ElastiCache.

flowchart LR writeApp[Write_app] --> writer[Writer] report[Reporting] --> rr[Read_replicas] writer -->|async| rr

Use case 3 — Multi-Region DR with low RPO (Aurora)

Need: Secondary Region, RPO about a second, RTO of minutes, least ops.

Design: Aurora Global Database. Not hourly snapshot copy. Classic cross-Region RDS replicas work but usually mean more lag and more manual promote story.

Case study 1 — Multi-AZ vs replica

Stem

A production PostgreSQL database on RDS must stay available if one Availability Zone fails. Reporting can stay slightly behind. Leadership does not ask for another Region. What do you enable first?

A — wrong A cross-Region read replica only — “that covers everything.”
B — correct Multi-AZ deployment for automatic failover in the Region. Add a read replica later if reporting needs scale.
C — wrong Point the app at a read replica and call that failover.
D — wrong Disable automated backups to speed up writes.

AZ failure in one Region is Multi-AZ’s job. Cross-Region is Multi-Region DR, not the ask. Replicas are async and not the automatic same-endpoint HA story. Backups off hurts recovery and can block features.

Case study 2 — Lambda connection storm

Stem

A bursty Lambda function writes to Aurora. During peaks the database hits max connections and errors. Reads are fine. Secrets should not live in the function package. What helps most?

A — wrong Add five Aurora read replicas and send Lambda to the reader endpoint.
B — correct Put RDS Proxy in front of Aurora; use Secrets Manager / IAM auth with the proxy.
C — wrong Move all data to Memcached.
D — wrong Switch to Multi-AZ only — “failover will fix connections.”

Writes need the writer; replicas do not absorb writer connection storms. Memcached is not a durable store. Multi-AZ does not pool connections. Proxy is built for this.

Case study 3 — Aurora Multi-Region

Stem

Aurora MySQL in us-east-1 must support disaster recovery in eu-west-1 with RPO of about one second and RTO of minutes, with least operational effort. What fits?

A — wrong Multi-AZ in us-east-1 only.
B — wrong Manual snapshot copy to eu-west-1 every hour.
C — correct Aurora Global Database with a secondary Region in eu-west-1.
D — wrong ElastiCache Global Datastore as the database of record.

Multi-AZ is same-Region. Hourly snapshots miss the RPO. Cache is not the system of record. Global Database matches the RPO/RTO and ops story.

Tricky points (still explained simply)

Multi-AZ standby is not a reader on classic RDS instance deployments. Do not load-balance writes or reports onto it.

Read replicas are asynchronous. Promotion is a deliberate DR/migration step; expect lag and a new writer story unless you re-point DNS carefully.

Multi-Region is a different problem than Multi-AZ. Same-Region HA first; cross-Region only when the stem asks for another Region or DR.

Encryption cannot be toggled on in place for unencrypted RDS — snapshot, encrypted copy, restore.

PITR creates a new instance — it is recovery, not an in-place undo of one bad row on the live endpoint.

RDS Proxy ≠ ElastiCache. Connections vs cached data.

Redis ≠ Memcached. Structures, optional persistence, and HA vs simple volatile cache.

Light touch on the exam Every Aurora Parallel Query knob, OEM option groups, exact failover second counts. Know Multi-AZ / replica / Global / Proxy / cache contrasts.
