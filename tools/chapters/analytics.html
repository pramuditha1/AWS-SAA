Analytics — lake in S3, then pick the engine

Should-knowDomain 3 · Athena, Redshift, Glue, EMR, OpenSearch

On SAA, analytics is a matching game. The data lake usually lives in S3. You then pick who queries it: serverless SQL (Athena), a warehouse (Redshift), Spark/Hadoop (EMR or Glue), or search (OpenSearch). Humans see results in QuickSight. Lake Formation governs who sees which columns.

Start here — the W questions

Why

Application databases are bad warehouses. You need a place for history, logs, and events — and tools that scan terabytes without melting the OLTP database.

What

A small family: S3 lake + Glue catalog, Athena, Redshift (+ Spectrum), Glue ETL, EMR, OpenSearch, Lake Formation, QuickSight. Streaming ingest often uses Kinesis/Firehose (covered under messaging).

Where

Mostly Regional. Objects in S3; clusters and serverless query engines in a Region. QuickSight is a BI layer on top.

Which pieces matter

Athena scan cost · Parquet · Glue catalog/crawlers · Redshift vs Athena · EMR when Spark is named · OpenSearch for full-text · Lake Formation grants · QuickSight dashboards.

Core knowledge (beginner foundations)

Lake first, engine second

Land raw and curated files in S3. Register tables in the Glue Data Catalog (names, columns, formats, partitions). Athena, Spectrum, and EMR can share that catalog. Format matters: columnar Parquet/ORC with partitions scans far less than fat JSON.

Athena — serverless SQL over S3. Pay per data scanned. Best for ad-hoc and intermittent queries.

Redshift — managed columnar warehouse for concurrent BI. Load with COPY from S3. Spectrum queries lake data still in S3.

Glue — catalog + serverless ETL (Spark). Crawlers discover schemas.

EMR — managed Hadoop/Spark/Hive cluster when you need that ecosystem or long-running big-data platforms.

OpenSearch Service — full-text search and log analytics UIs — not a SQL warehouse.

How the lake pattern fits (from AWS docs)

Follows the common lake architecture described across What is Amazon Athena? and What is AWS Glue?.

Remember “SQL on S3, least ops, pay per scan” → Athena + Parquet. “Many analysts, complex warehouse” → Redshift. “Existing Spark jobs / Hadoop” → EMR. “Full-text search” → OpenSearch.

Use case 1 — ad-hoc SQL on logs

Need: Query JSON logs in S3 a few times a week; no cluster babysitting.

Design: Convert to partitioned Parquet (Glue job), crawl into Glue catalog, query with Athena. Optional QuickSight.

Use case 2 — enterprise BI warehouse

Need: Hundreds of analysts, predictable SQL latency, nightly facts.

Design: Redshift (or Serverless), COPY from S3, Spectrum for cold history in the lake.

Use case 3 — column-level lake security

Need: Analysts query sales in Athena but must not see SSN columns.

Design: Lake Formation permissions on Glue tables/columns; lock S3; Athena honors the grants.

Case study 1 — Athena cost

Stem

Ad-hoc SQL over 20 TB of JSON in S3 once a month. Least operations and lower scan cost.

A — wrong Large Redshift cluster left running all month.
B — correct Convert to Parquet + partitions, Glue catalog, Athena.
C — wrong OpenSearch for SQL warehouse-style joins.
D — wrong RDS and load all 20 TB into InnoDB.

Case study 2 — Spark platform

Stem

Data science team has existing Spark jobs, bootstrap needs, and Spot task nodes. They refuse to rewrite for Glue yet.

A — wrong Athena only.
B — correct Amazon EMR with Spark and Spot for task capacity.
C — wrong QuickSight SPICE import of raw TB-scale JSON.
D — wrong DynamoDB.

Case study 3 — search vs warehouse

Stem

Product catalog needs fuzzy full-text search for the storefront. Separately, finance needs a SQL warehouse.

A — wrong One Redshift cluster for fuzzy search UX.
B — correct OpenSearch for product search; Redshift (or Athena) for finance SQL.
C — wrong Only CloudWatch Logs Insights for the catalog.
D — wrong Lake Formation alone without a query engine.

Tricky points (still explained simply)

Athena cost = bytes scanned. SELECT * on JSON is an expensive habit. Project columns; use Parquet.

Redshift is OLAP, not OLTP. Do not put the shopping-cart database there.

Glue has two jobs: catalog and ETL. Do not forget the catalog when the stem says “discover schema.”

Kinesis/Firehose feed the lake or OpenSearch; they are not warehouses.
