Containers — ECS, EKS, Fargate, and ECR

Must-knowDomains 2–4 · run containers without reinventing the fleet

Containers package your app and its libraries so “it works on my laptop” becomes “it works on the platform.” On AWS you still choose an orchestrator (ECS or EKS) and a compute mode (EC2 you manage, or Fargate that AWS runs). The exam is mostly that fork plus IAM task roles and where images live (ECR).

Start here — the W questions

Why

VMs are heavy when you ship many small services. Containers start fast and pack denser. Teams also want the same image in test and prod. Someone still has to schedule, restart, and scale those containers.

What

Amazon ECS is AWS’s native orchestrator. Amazon EKS is managed Kubernetes. Fargate is serverless compute for tasks/pods — you do not patch container host EC2. ECR is the private image registry.

Where

Clusters are Regional. Tasks/pods run in your VPC subnets (Fargate uses awsvpc networking). Images sit in ECR in a Region (replicate if needed).

Which pieces matter

Task definition · service · Fargate vs EC2 launch · task role vs execution role · ALB integration · EFS for shared files · ECS vs EKS choice. Those cover most SAA container stems.

Core knowledge (beginner foundations)

Orchestrator vs compute

Think of two knobs. Orchestrator decides desired count, restarts, and service discovery (ECS or EKS). Compute is where the container process runs (your EC2 capacity, or Fargate). You can mix: ECS+Fargate, ECS+EC2, EKS+Fargate, EKS+EC2.

Image — the packaged filesystem + metadata. Built from a Dockerfile; stored in ECR.

Task definition (ECS) — blueprint: image, CPU/memory, ports, IAM roles, logging.

Task — one running copy. Service — keep N tasks healthy and attach them to a load balancer.

Pod (EKS) — Kubernetes’ unit (one or more containers). Same Fargate idea: AWS runs the worker OS.

Task role — permissions for the application (read S3, write SQS). Task execution role — permissions for the agent (pull from ECR, write logs). Mixing them up is a classic trap.

ECS vs EKS

Pick ECS when the stem wants AWS-native simplicity and deep ALB/IAM/CloudWatch integration. Pick EKS when the stem requires Kubernetes APIs, existing Helm charts, or multi-cloud k8s skills. Both can use Fargate. Elastic Beanstalk can run Docker with even less control — use when they want PaaS, not raw orchestration.

Remember “Least operational overhead for containers” → ECS or EKS on Fargate. “GPU containers” → EC2 launch type. “App needs S3 access” → task role, not only the instance profile.

Use case 1 — simple API on Fargate

Need: Stateless API, least server management, HTTPS via ALB.

Design: ECS service on Fargate, awsvpc ENIs in private subnets, ALB in public subnets, images in ECR, logs to CloudWatch.

Use case 2 — shared files between tasks

Need: Several tasks read/write the same files.

Design: Mount EFS in the task definition (works with Fargate). EBS is per-task attachment, not a shared NFS for many tasks.

Use case 3 — existing Kubernetes platform

Need: Keep Helm, Operators, and kubectl workflows.

Design: EKS; choose Fargate profiles or managed node groups. Still use ECR (or another registry).

Case study 1 — least ops

Stem

Run a containerized web app. Team has no desire to manage AMIs or SSH. Scale on CPU. Images stay private.

A — wrong ECS on self-managed EC2 with no Autoscale story for instances.
B — correct ECS (or EKS) on Fargate, ECR, ALB, Service Auto Scaling on CPU.
C — wrong Spot EC2 only without orchestration.
D — wrong Lambda — 15-minute limit and different packaging; stem said containers as the unit.

Case study 2 — task role

Stem

Fargate tasks must read one S3 bucket. What grants the app credentials?

A — wrong Put access keys in the image environment.
B — correct Task IAM role with s3:GetObject on that bucket.
C — wrong Only the task execution role — that pulls images/logs, not app S3 reads.
D — wrong Make the bucket public.

Case study 3 — ECS vs EKS

Stem

Company standard is Kubernetes; hundreds of Helm charts already exist. They want managed control plane on AWS.

A — wrong Rewrite everything for ECS task definitions this quarter.
B — correct Amazon EKS (Fargate or node groups as needed).
C — wrong Elastic Beanstalk single-instance Docker only.
D — wrong App Runner when the stem insisted on Kubernetes.

Tricky points (still explained simply)

Fargate still needs a VPC. Serverless here means “no EC2 hosts to patch,” not “no networking.”

Dynamic ports + ALB matter more on EC2 launch type packing; Fargate tasks typically map cleanly with awsvpc.

ECS Anywhere / EKS Anywhere — name-level: run AWS-orchestrated containers on-premises. Do not confuse with Outposts.

Beanstalk vs ECS. Beanstalk is PaaS convenience; ECS/EKS are when you need container orchestration control.
