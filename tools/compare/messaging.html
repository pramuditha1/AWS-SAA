Messaging picker — queue, bus, stream, or workflow

High-score pageDomain 2.3 · decoupling · Domain 3 event-driven

Messaging questions look alike until you name the shape of the conversation. A queue buffers work for competing workers. A topic or bus fans one event out to many targets. A stream is a replayable log. A state machine orchestrates steps with retries. Pick the shape first. The product name follows.

Start here — the W questions

Why

If a web server calls a worker directly, a spike or a crashed worker breaks the user. A queue or bus absorbs the spike, lets workers die and retry, and lets new subscribers appear without rewriting the producer.

What

This picker chooses among SQS (queue), SNS (topic), EventBridge (bus with rules), Kinesis Data Streams / MSK (replayable log), Firehose (delivery into S3/analytics), Step Functions (orchestrator), and Amazon MQ (keep JMS / ActiveMQ / RabbitMQ).

Where

These services are Regional and Multi-AZ under the hood. You call Regional endpoints. Cross-account and SaaS partners often meet you on an EventBridge bus. MQ brokers sit in your VPC.

Which pieces matter

Queue vs fan-out vs stream · SQS Standard vs FIFO · SNS + SQS durable fan-out · EventBridge content rules · Kinesis retention / replay · Firehose destinations · Step Functions · Amazon MQ for legacy brokers. Those ideas cover almost every messaging stem.

Core knowledge — how to walk a stem

Ask three shape questions

1. Do many independent systems each need a copy of the same event (and maybe at different speeds)? That is fan-out — not one shared queue. 2. Must a later app replay last week’s data? Queues delete after success; streams retain. 3. Is this a multi-step business workflow with branches and retries? That is Step Functions, not nested Lambdas.

Competing consumers vs fan-out. Three workers on one SQS queue fight over messages — each message goes to one worker. That is not fan-out. Fan-out is SNS or EventBridge. If a slow fleet must not lose work, subscribe an SQS queue to the topic/bus (SNS → SQS → workers), not only a raw HTTP endpoint.

Replay. After SQS delete, the message is gone. Kinesis Data Streams keeps a retention window (default 24 hours, up to 365 days) so a new analytics app can rewind. Clickstream + multiple independent readers → Kinesis (or MSK if they must keep the Kafka API).

Order and duplicates. SQS Standard = at-least-once, best-effort order — write idempotent workers. SQS FIFO = order per message group ID + exactly-once processing inside the dedup window. Visibility timeout hides in-flight work; after maxReceiveCount failures, send poison messages to a dead-letter queue (DLQ).

Case study 1 — fan-out that cannot lose work

Stem

Order events must fan out to a fraud Lambda, an email notification, and a durable worker fleet that can lag during peaks. No message may be lost if a worker is down.

A — wrong One SQS queue consumed by all three. Competing consumers: email or Lambda would steal messages from the workers.
B — correct SNS topic with subscriptions to Lambda, email, and an SQS queue for the workers. SQS is the durable buffer.
C — wrong EventBridge to Lambda and email only, no queue. Routing is fine, but a down worker fleet needs a buffer (you could add an SQS target — without it this fails the stem).
D — wrong Kinesis Data Streams. Valid for replay + many shard readers. The stem did not ask for that. Wrong default.

Memorize: fan-out + durable slow consumer = SNS (or EventBridge) plus SQS.

Case study 2 — replayable clickstream

Stem

A website emits millions of click events per hour. Today a fraud app consumes them. Next quarter a data-science team must replay the last seven days into a new model without asking the website to emit twice. Ordering per user is desirable.

A — wrong SQS Standard. After the fraud app deletes a message it is gone. A new consumer cannot replay last week.
B — correct Kinesis Data Streams with retention ≥ 7 days. Independent consumers read the same shards. Partition key = user id for per-user order.
C — wrong SNS only. Push delivery, no week-long retention log for replay.
D — wrong Amazon MQ. You would run a broker to fake a stream.

Already on Kafka and cannot change → MSK. Only need to land clicks in S3 for Athena → Firehose can be enough, but Firehose is not a replay API for a second real-time app.

Case study 3 — order must not jump the queue

Stem

A payments processor must process events for a given account in order, with no duplicates even if the producer retries. Throughput per account is modest. Spikes are absorbed by a buffer. Workers are EC2.

A — correct SQS FIFO with message group ID = account ID, plus the producer’s deduplication ID (or content-based dedup). Workers long-poll the FIFO queue.
B — wrong SQS Standard plus “workers sort in memory.” Standard is at-least-once and best-effort order.
C — wrong Kinesis with a single shard for the whole system. Ordering works, but you invent a throughput ceiling; SQS FIFO matches “buffer + workers” with fewer moving parts.
D — wrong SNS Standard topic. No ordering, no competing-worker buffer.

Per-account order at modest rate is FIFO. Millions of globally ordered messages often points to Kinesis partition keys instead.

Tricky points

At-least-once → idempotent consumers. Visibility timeout too short → duplicate processing. Too long → slow recovery after a crash. DLQ for poison pills.

EventBridge vs SNS. SNS = topics you publish to. EventBridge = AWS service events, SaaS partners, content filters, archive/replay, Scheduler. Both can fan out. EventBridge wins on “when EC2 state changes,” “Salesforce events,” or “filter on a JSON field.”

Kinesis vs SQS vs Firehose. Workers pulling jobs → SQS. Many apps replaying a log → Kinesis. Dump into S3/Redshift with no app → Firehose. Never use Firehose as a job queue.

Step Functions vs SQS. SQS is a buffer. Step Functions is a workflow (“wait for human, call two APIs in parallel, retry this one”).

Amazon MQ is compatibility. New designs use SQS/SNS/EventBridge. MQ appears when the stem forbids changing the JMS client.
