Compute picker — VM, function, container, or PaaS

High-score pageDomains 3.1 & 4.2 · pick compute, then pick how you pay

Compute questions collapse to a few hard limits. Do you need a full operating system? Is the work a short event? Is the deploy unit a container? How much ops will you accept? After you pick the service, the cost half asks On-Demand vs Savings Plans / Reserved vs Spot.

Start here — the W questions

Why

Always-on VMs waste money when work is idle. Tiny event jobs do not need Kubernetes. Existing Docker images do not need a full OS rewrite. Picking the wrong shape either burns cash at 3 a.m. or hits a hard limit mid-exam.

What

This picker chooses among EC2 (VM), Lambda (event function), ECS / EKS (containers), Fargate (containers without managing hosts), Batch (queued jobs), and Elastic Beanstalk (PaaS on EC2/ELB). Then it picks how you buy capacity.

Where

Compute runs in a Region and usually in one or more AZs. Lambda is Regional and scales for you. Fargate tasks and EC2 instances sit in your VPC subnets when you place them there. Spot capacity can vanish with a two-minute notice.

Which pieces matter

OS / SSH / GPU needs · Lambda 15-minute wall · ECS vs EKS · Fargate launch type · Batch for queued jobs · Beanstalk for “upload code” · On-Demand / Savings Plan / RI / Spot. Those ideas cover almost every compute stem.

Core knowledge — how to walk a stem

Kill illegal answers first

Longer than 15 minutes → not Lambda (unless the stem invites Step Functions + more Lambdas). Need Kubernetes API / Helm / existing operators → EKS, not ECS. Containers + least ops + no k8s → ECS on Fargate. Need SSH, a custom kernel, a vendor installer, or a GPU shape Lambda does not offer → EC2 (or Batch on EC2/Spot).

Idle cost next. Always-on EC2 or an ECS service with desiredCount > 0 costs money at night. Lambda scales to zero. Fargate also can scale in — but a service kept at three tasks is not “free at idle.” Spot is the cheapest EC2 capacity and can be interrupted; mix an On-Demand/Reserved baseline with Spot for fault-tolerant fleets. Do not put a single-node database on Spot.

Purchase options (Domain 4). On-Demand = no commitment. Compute Savings Plans cover EC2, Fargate, and Lambda flexibly. EC2 Instance Savings Plans / Reserved Instances = deeper discount, less flexible. Spot ≈ large discount, interruptible. Dedicated Hosts = socket/core-tied BYOL. Capacity Reservations = guarantee capacity, not a discount by themselves. Steady 24/7 + spiky queue → commit for the baseline, Spot/ASG for the spike — never RI the peak.

Case study 1 — thumbnail that sleeps

Stem

Images uploaded to S3 must be thumbnailed within seconds. Work lasts 20–40 seconds. Traffic is spiky. Least operational overhead and least cost at idle.

A — correct S3 event notification → Lambda. Well under 15 minutes. Scale to zero. Canonical event-driven pattern.
B — wrong Always-on EC2 fleet. You pay at idle. More patching, no benefit the stem asked for.
C — wrong ECS on EC2 with a minimum of three tasks. Still capacity at idle. Fine if work exceeded Lambda limits — it does not.
D — wrong AWS Batch on large Spot clusters. Batch is for queued jobs of minutes to hours. Extra moving parts for a 30-second thumbnail.

If work were 40 minutes, Lambda dies — move to Fargate / Batch / EC2 with SQS. Always re-check the 15-minute wall.

Case study 2 — containers, no k8s religion

Stem

A team has Docker images for a web API. They do not use Kubernetes today and do not want to learn it this quarter. They want AWS to run the containers, patch the hosts, and scale with CPU. The API is always on during business hours.

A — wrong EKS on EC2. Kubernetes was not requested and adds a control plane to operate.
B — correct Amazon ECS on AWS Fargate. Docker in, no AMIs to patch, Service Auto Scaling on CPU.
C — wrong Lambda with a container image. Possible for request/response within Lambda limits, but an always-on API with existing Docker often fits ECS/Fargate; the stem did not ask for events or scale-to-zero.
D — wrong Elastic Beanstalk with a ZIP of source. They already have Docker images; ECS is the native place to run them.

EKS when the stem says Kubernetes, Helm, or existing k8s workloads. Otherwise ECS + Fargate is the least-ops container path.

Case study 3 — steady core, interruptible overflow

Stem

A video-encoding fleet on EC2 runs 24/7 at about 40 instances and spikes to 200 when producers upload. Jobs are checkpointed and can restart. Leadership wants the lowest 12-month bill without missing baseline capacity.

A — wrong 200 On-Demand instances all year. Meets capacity, burns money at night.
B — correct Compute Savings Plan or Reserved capacity for the 40-instance baseline, plus an Auto Scaling group of Spot (with On-Demand fallback) for the spike. Checkpointed workers are the textbook Spot use case.
C — wrong All 200 on Spot. Baseline can vanish in a capacity crunch. The stem said do not miss baseline.
D — wrong Dedicated Hosts for the spike. Hosts are for socket-tied licensing, not cheap overflow.

Commit for steady state. Spot for interruptible burst. Keep a small On-Demand escape hatch. Do not RI the peak.

Tricky points

Lambda 15 minutes is a wall. Also watch sync payload size through API Gateway, /tmp size, and cold starts — Provisioned Concurrency is the “cannot tolerate cold start” add-on, not “always buy it.”

Fargate is not a third orchestrator. It is a launch type for ECS or EKS. “Fargate vs ECS” as mutually exclusive options is a poorly worded distractor; the correct combo is often ECS + Fargate.

Beanstalk vs ECS vs EKS vs App Runner. Beanstalk: I have source, make it a web app. ECS: I have Docker. EKS: I have Kubernetes. App Runner: most PaaS-like HTTP container/source service (lower weight on SAA).

Batch vs Step Functions vs SQS+ASG. Batch = job queues and Spot compute environments. Step Functions = business workflow across APIs. SQS+ASG = classic custom workers when they want the pieces visible.

Graviton / ARM is a cost/performance answer when the app supports it. Skip it if the binary is x86-only.
