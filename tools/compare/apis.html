API picker — stateless or stateful, pull or push

High-score pageDomains 2 & 3 · decoupling · real-time performance

API questions get easier once you know what kind of conversation the app needs. Does the client ask and wait (REST, GraphQL)? Does an event source call someone else's URL (webhook)? Or does the server need to push to a connection that stays open (WebSockets, GraphQL subscriptions)? Answer that, and the AWS service follows.

Start here — the W questions

Why

Some apps only need answers when they ask. Others need the server to speak first: a new chat message, a live score, a payment confirmation. Picking request/response when you needed push leads to wasteful polling. Picking open connections when you only needed request/response adds state you must manage.

What

Stateless APIs keep no memory of the client between requests: REST, webhooks, and GraphQL queries/mutations. Stateful APIs keep a connection open and remember the client: WebSockets and GraphQL subscriptions.

Where

On AWS these are Regional managed services: API Gateway (REST, HTTP, WebSocket APIs), AppSync (GraphQL and real-time), EventBridge API destinations (outgoing webhooks), and Lambda function URLs (simple HTTPS endpoint for one function).

Which pieces matter

Stateless vs stateful · pull vs push · who hosts the endpoint · REST vs HTTP API · WebSocket API routes and connection IDs · AppSync subscriptions · API destinations for webhooks · external session store for a stateless web tier.

Core knowledge — stateless vs stateful

One sentence each

Stateless: the server remembers nothing about you between requests, so every request carries its own token and context. Any server can answer it, which makes scaling easy. Stateful: the server keeps an open connection or session for you, so it can push data the moment something happens. The cost is that someone has to track every connection.

"Stateless" is about the connection, not the data. A stateless REST API still writes to DynamoDB. It just does not remember the caller between requests.

Where GraphQL fits. GraphQL is a query language: the client asks one endpoint for exactly the fields it wants, so it doesn't over-fetch or make several REST round trips. Queries (read) and mutations (write) are ordinary HTTP requests, so they are stateless like REST. Subscriptions add real time. The client keeps a WebSocket open, and the server pushes whenever the subscribed event happens. In AWS AppSync, a subscription fires when a matching mutation runs.

How an API Gateway WebSocket API works

API Gateway keeps the open connection for you. Your Lambda functions stay stateless. Each client gets a connection ID, which you store in DynamoDB. Messages are routed by a field in the JSON body (the route selection expression, for example $request.body.action). To push to a client, the backend POSTs to the @connections callback URL with that client's connection ID.

Case study 1 — live chat

Stem

A support chat must deliver each message to the other participant within a second. Traffic is spiky, and the team wants no servers to manage. Which design fits best?

A — wrong API Gateway REST API; each browser polls for new messages every second.
B — correct API Gateway WebSocket API + Lambda; connection IDs in DynamoDB; the backend pushes through @connections.
C — wrong SNS SMS to each participant.
D — wrong Kinesis Data Streams read directly by browsers.

Chat needs the server to push, so a stateful, two-way connection is the shape. Polling (A) wastes requests and adds delay. SMS (C) is not an in-app channel. Browsers do not read Kinesis shards (D). The WebSocket API holds the connections, so Lambda stays stateless.

Case study 2 — webhook to a partner

Stem

When an order ships, a logistics partner must receive an HTTPS POST at their endpoint. The partner requires an API key, accepts at most 10 requests per second, and failed calls must be retried. Least custom code.

A — wrong Put events on an SQS queue and ask the partner to poll it.
B — wrong AppSync subscription that the partner connects to.
C — correct EventBridge rule → API destination with a connection (API key auth), invocation rate limit 10/s, retry policy and DLQ.
D — wrong Cron Lambda that batches orders hourly and emails a CSV.

A webhook is stateless push to a URL the receiver hosts. API destinations do exactly that, with auth, rate limiting and retries built in. A and B make the partner pull or hold a connection, which they did not offer. D breaks the per-event requirement.

Case study 3 — sessions lost on scale-in

Stem

A web app on an Auto Scaling group behind an ALB stores user sessions in instance memory. When the group scales in, users are logged out. How do you fix this and keep scaling elastic?

A — wrong Turn on sticky sessions and stop scaling in.
B — correct Store sessions in ElastiCache (Redis) or DynamoDB so the web tier becomes stateless.
C — wrong Larger instances so fewer are needed.
D — wrong Save sessions on each instance's EBS volume.

Sessions kept in memory make each server stateful. Moving them to a shared store lets any instance serve any user. Sticky sessions (A) still lose the session when that instance dies. EBS (D) is attached to one instance, so it has the same problem.

Tricky points

Webhooks are push, but stateless. Each event is one HTTP call to a URL the receiver hosts. No connection stays open between events.

GraphQL is not automatically real-time. Queries and mutations are plain HTTP. Only subscriptions keep a WebSocket open.

WebSocket API ≠ stateful Lambda. API Gateway holds the connection. Your functions stay stateless and look up connection IDs in DynamoDB.

Connections expire. API Gateway closes WebSockets after 10 minutes idle or 2 hours total. Clients must reconnect, so a long job's result should not depend on one open socket.

29-second limit. REST/HTTP integrations time out at about 29 seconds by default. For long work, accept the request, process asynchronously, and notify by WebSocket, webhook, or polling.

Sticky sessions are a crutch. They keep a stateful tier working, but an external session store is the scalable answer.
