Storage picker — which store matches the app

High-score pageDomains 3.1 & 4.1 · object, block, file, hybrid

A storage question is a matching game. The app already speaks a language — objects over HTTP, a disk, NFS, or SMB. You pick the AWS service that speaks that language and still meets durability and cost. The cheaper answer that drops one constraint is almost always the trap.

Start here — the W questions

Why

One “storage” product cannot fit every app. A website needs unlimited object keys. A database needs a block disk. Linux fleets need a shared home directory. Windows desktops need SMB. Mixing those up is how exams score wrong answers.

What

This picker helps you choose among S3 (objects), EBS / instance store (block), EFS (NFS file), FSx (Windows / Lustre / NetApp / OpenZFS), Storage Gateway (hybrid protocol), DataSync (online copy), and Snow (ship a box).

Where

Most choices are Regional. EBS lives in one AZ (attach to instances in that AZ). Regional EFS and normal S3 classes keep copies across AZs. One Zone classes and a single EBS volume die with that AZ. Multi-Region needs replication or a second copy you design.

Which pieces matter

Protocol first · AZ vs Region failure · POSIX vs object · S3 storage class · EFS Regional vs One Zone · FSx family by protocol · Gateway vs DataSync vs Snow. Those ideas cover almost every storage stem.

Core knowledge — how to walk a stem

Three passes over the question

Read once for the protocol (what the app already speaks). Read again for the failure domain (survive one AZ? recreate the data?). Read a third time for cost — only after every hard constraint is met. Never start with “which is cheapest.”

Protocol clues. “Objects,” “static website,” “data lake,” “11 nines,” “lifecycle to Glacier” → S3. “Boot volume,” “database disk,” “attach to one instance” → EBS. “Highest IOPS, temporary, lose on stop” → instance store. “POSIX home directories,” “thousands of Linux instances,” “NFS,” “Multi-AZ file share” → EFS Regional. “SMB,” “Active Directory,” “Windows mapped drives” → FSx for Windows. “HPC scratch,” “Lustre,” “S3 as the repository” → FSx for Lustre. “On-premises keeps NFS/SMB/iSCSI, data lands in AWS” → Storage Gateway. “Copy the NAS to S3 this week, then nightly sync” → DataSync. “Petabytes, pipe too small, ship hardware” → Snow.

Failure domain. If data must survive an AZ loss, kill One Zone-IA, EFS One Zone, and a lone EBS volume in one AZ. EBS Multi-Attach is same-AZ only and is not a clustered file system by itself. Regional EFS and S3 Standard / Standard-IA store data across AZs.

Cost last. EFS usually costs more per GB than S3. Instance store is “free” with the instance but dies on stop. That is fine for scratch; illegal as the only copy of customer data.

Quick triangle. S3 = HTTP objects, cheapest bulk, no real POSIX. EFS = NFS, elastic, Multi-AZ, shared Linux. EBS = one instance (usually), provisioned IOPS, snapshots to S3.

Gateway modes (when hybrid stays): File Gateway (NFS/SMB → S3), Volume Gateway (iSCSI → snapshots), Tape Gateway (VTL → S3/Glacier). Cached keeps hot data locally; stored keeps the full set locally and backs up.

Case study 1 — shared POSIX that survives an AZ

Stem

Ten Linux app servers run in two Availability Zones. They must share home directories with POSIX permissions and file locking. Data must survive the loss of one AZ. Cost should be reasonable. Which storage?

A — wrong EBS Multi-Attach io2. Multi-Attach is same-AZ only. Two writers on a raw volume without a clustered file system corrupt it.
B — correct Amazon EFS Regional. NFS, POSIX, Multi-AZ. This is the documented shared Linux file system across AZs.
C — wrong FSx for Windows. SMB and Active Directory. The fleet is Linux and asked for POSIX/NFS.
D — wrong S3 with a FUSE mount. Object storage is not a POSIX home directory (locking, chmod, consistency).

Protocol first (NFS/POSIX), then failure domain (two AZs). Multi-Attach looks like “shared disk” and is the classic trap.

Case study 2 — lift a Windows file server

Stem

A Windows file server on-premises is joined to Active Directory. Thousands of desktops map a drive over SMB. They want a managed AWS service, Multi-AZ, and no client rewrite. Backups should feel like snapshots they already know.

A — wrong Amazon EFS. NFS and Linux-oriented. The stem said SMB and AD.
B — correct FSx for Windows File Server, joined to AD, Multi-AZ, Volume Shadow Copy style snapshots.
C — wrong S3 File Gateway only. File Gateway can present SMB, but it is a hybrid cache into S3, not a first-class Multi-AZ Windows file server with NTFS semantics.
D — wrong FSx for Lustre. HPC scratch, wrong protocol.

“SMB + Active Directory + Windows” is FSx for Windows unless the stem adds NetApp ONTAP features (then FSx for ONTAP).

Case study 3 — NAS to S3 without a truck

Stem

A hospital has 80 TB on a NAS. The WAN can push about 500 Mbps. They need a one-time copy into an S3 data lake this month, then nightly incrementals. The NAS stays the source of truth until cutover.

A — wrong Snowball. Valid when the pipe cannot finish in time. Here the WAN works and they want nightly sync — Snow is not a nightly sync tool.
B — correct AWS DataSync to S3, then a scheduled DataSync task for incrementals. This is the documented online NFS/SMB copy service.
C — wrong Storage Gateway alone. Gateway is a standing protocol translator/cache, not the bulk migration service AWS names for NAS-to-S3 copy.
D — wrong AWS DMS. Databases, not NAS files.

Bandwidth × time decides Snow vs DataSync. Recurring sync after the first copy is DataSync.

Tricky points

EBS Multi-Attach ≠ Multi-AZ. Same AZ, clustered FS required. Two AZs → EFS or FSx Multi-AZ.

Instance store vs EBS. Stop, hibernate, or hardware failure can wipe instance store. “Must persist” → EBS. “Highest temporary IOPS” → instance store.

S3 is not a file system. Data lake, backups, media, static site — yes. Home directories and Windows mapped drives — no, unless Gateway or FSx sits in front.

One Zone is cheaper and dies with the AZ. Fine for recreatable data. Illegal as the only copy of something you cannot rebuild.

gp3 is the default EBS answer now. io2 Block Express is the SAN-like / highest durability volume answer. st1 = sequential throughput; sc1 = cold HDD.
