Database picker — match the API, then match HA

High-score pageDomain 3.3 · purpose-built · Domain 2 HA

AWS wants a purpose-built database for the access pattern, not one giant relational box for everything. First match the API the app already uses. Then decide if the pain is AZ failover, extra reads, or a whole Region. Those three knobs are different. Mixing them up is how the exam catches you.

Start here — the W questions

Why

SQL joins, key-value at millions of QPS, a Mongo driver, a graph of fraud rings, and a BI warehouse are different jobs. Forcing them all into one engine makes you rewrite apps or fail under load.

What

This picker chooses among RDS / Aurora (SQL), DynamoDB (key-value / document), ElastiCache / DAX / MemoryDB (cache), DocumentDB, Neptune, Keyspaces, and Redshift (warehouse) — then the HA and scale add-ons.

Where

Engines are Regional. Multi-AZ keeps a standby in another AZ in the same Region. Read replicas can be same-Region or cross-Region. Aurora Global and DynamoDB Global Tables are Multi-Region. Multi-AZ is not disaster recovery for Region loss.

Which pieces matter

API / access pattern · Multi-AZ vs read replica vs Multi-Region · Aurora vs RDS · DynamoDB + DAX · RDS Proxy · ElastiCache vs MemoryDB. Those six ideas cover almost every database stem.

Core knowledge — how to walk a stem

Three questions in order

1. Must the app keep its current SQL / Mongo / Cassandra / Gremlin API? If yes, you may not pick DynamoDB. 2. Is the pain HA for writes in one Region, more read capacity, or Region failure? 3. Is the data only a cache (OK to lose) or the system of record?

API first. “Minimal change” + MySQL/Postgres → RDS or Aurora. + MongoDB drivers → DocumentDB. + Cassandra/CQL → Keyspaces. + Gremlin/SPARQL graph → Neptune. Key-value, single-digit ms, huge scale, no joins → DynamoDB. Joins across petabytes for BI → Redshift.

HA vs reads vs DR. RDS Multi-AZ (or Aurora storage + failover) = automatic failover for writes inside one Region, same endpoint. A read replica is asynchronous — good for reads or as a DR seed; promotion is a DR action, not automatic HA for the writer. Aurora Global Database and DynamoDB Global Tables are the Multi-Region answers. Multi-AZ does not save you when the Region goes dark.

Cache or not. Sessions, leaderboards, sub-millisecond, OK to rebuild → ElastiCache Redis/Valkey (Memcached for simple multi-engine, no persistence). Redis and durable in-memory → MemoryDB. Microsecond DynamoDB reads → DAX (DynamoDB API only — not a Redis in front of RDS).

Case study 1 — failover without a rewrite

Stem

An existing PostgreSQL application needs automatic failover inside one Region. The team will not rewrite SQL. Reporting can stay on the primary for now. RPO for AZ failure should be essentially zero.

A — correct RDS Multi-AZ instance deployment. Synchronous standby, same endpoint after failover, no SQL rewrite.
B — wrong A single read replica in a second AZ. Replication is async. Failover is a promotion. Writes can be lost. That is not automatic HA for writes.
C — wrong DynamoDB. Different API. The app is PostgreSQL.
D — wrong ElastiCache Redis. A cache is not the system of record.

Aurora PostgreSQL also works and wins if they add “storage across three AZs, faster failover, auto-growing storage.” With these constraints, RDS Multi-AZ is enough — do not over-upgrade.

Case study 2 — key-value at any scale

Stem

A mobile game stores player session state as a key-value document. Peak is millions of QPS, load is spiky and unknown, and they want to pay little when idle. Reads and writes must stay in single-digit milliseconds. No joins.

A — wrong RDS MySQL with a huge instance and replicas. Expensive at idle and a poor fit for millions of QPS key-value.
B — correct DynamoDB on-demand (or provisioned with auto scaling). Documented serverless key-value at single-digit millisecond scale.
C — wrong Amazon Redshift. Warehouse, seconds-scale queries — not a session store.
D — wrong ElastiCache only, with no durable store. Session loss on node failure is not said to be OK.

Later: microsecond DynamoDB reads → add DAX. Active-active two Regions → Global Tables. Do not add extras the stem did not ask for.

Case study 3 — Lambda hammering RDS

Stem

A serverless API uses Lambda against an existing RDS MySQL database. During spikes, Lambda concurrency exhausts max_connections. The schema cannot move this quarter. Failover should not break every connection.

A — wrong Only a bigger instance. Raises the ceiling and the bill; does not pool thousands of short Lambda connections.
B — correct Amazon RDS Proxy between Lambda and RDS. Connection pooling and multiplexing, with better behavior across failover.
C — wrong SQS in front of RDS so Lambda never talks to the DB. That forces an async redesign the stem did not ask for.
D — wrong Migrate immediately to DynamoDB. Schema cannot move this quarter.

When connections are the failure mode, the named answer is RDS Proxy. Aurora Serverless v2 can absorb load but does not replace pooling.

Tricky points

Multi-AZ ≠ read replica ≠ Multi-Region. HA for writes in one Region: Multi-AZ or Aurora. Extra reads: replica or cache. Survive Region loss: cross-Region replica, Aurora Global, DynamoDB Global Tables — plus backups, because replication copies corruption.

You cannot read the classic Multi-AZ standby. Need reads from another AZ → replica, Multi-AZ DB cluster, or Aurora reader.

Strongly consistent DynamoDB reads are same-Region. Global Tables across Regions are eventually consistent.

DAX vs ElastiCache. DAX speaks DynamoDB. ElastiCache is Redis/Memcached. Do not put DAX in front of RDS.

MemoryDB vs ElastiCache Redis. MemoryDB = Redis-compatible with Multi-AZ durability of the in-memory data. ElastiCache remains the default cache.
