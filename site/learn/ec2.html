Amazon EC2 — a virtual server you rent by the hour

Must-knowDomains 3 & 4 · Performance · Cost

Amazon EC2 is a virtual machine in the cloud. You choose the operating system, the size, how you pay, and which subnet it lives in. On the exam you match a workload to a family, a purchase option, and a multi-AZ design — not every instance type name.

Start here — the W questions

Why

Sometimes you need a real operating system you control: custom software, long-running processes, or a shape of CPU and memory that a managed service does not offer. You still need that machine to be replaceable, cheap enough, and not a single point of failure.

What

An EC2 instance is a rented virtual server. AWS owns the hardware. You pick an AMI (Amazon Machine Image — the template for the OS and root disk), an instance type, a subnet, security groups, and usually an IAM role. You are responsible for the guest OS and the apps on it.

Where

EC2 is Regional. Each instance lives in one subnet, so one Availability Zone. High availability means several instances in several AZs — never “one big server with an Elastic IP.”

Which pieces matter

AMI · instance family · purchase option (On-Demand / Spot / Savings Plans) · placement group · IAM instance profile + IMDS · EBS vs instance store. Those ideas cover almost every SAA EC2 question.

Core knowledge (beginner foundations)

An instance in one breath

You launch from an AMI into a subnet. AWS attaches a network interface (ENI) in that AZ, attaches storage, and boots the OS. Your app talks to AWS APIs using temporary credentials from the instance metadata service (IMDS) if you attached an IAM role — not long-lived keys baked into the disk.

AMI — a Region-scoped template: OS, root volume layout, and sometimes Marketplace software. Same golden image in another Region means copy the AMI (you cannot reuse the AMI ID across Regions).

Instance type — family + size (for example m7g.xlarge). Family is the personality: balanced, compute-heavy, memory-heavy, burstable, GPU, and so on.

User data — a small bootstrap script (about 16 KB max) that usually runs once at first boot. Do not put passwords there; use Secrets Manager or SSM Parameter Store with the instance role.

EBS vs instance store — EBS volumes survive stop. Instance store is local disk that dies when the instance stops or the host fails. Durable data belongs on EBS, EFS, S3, or a database — not only on instance store.

How an instance comes up (from AWS docs)

AWS describes launch as: pick AMI and type → place in a subnet → attach networking and storage → boot → optionally run user data. The Mermaid below follows that idea.

Instance families — pick the shape, not the marketing name

You do not need every generation. You need why each family exists, because stems hide the answer in the workload description.

FamilyIn plain EnglishTypical stem
T (burstable)Cheap baseline CPU; credits for short spikesDev/test, low and spiky traffic
M (general)Balanced CPU and RAMDefault app servers
C (compute)More CPU per dollarBatch, encode, high request rate, little RAM
R (memory)More RAM per vCPULarge heaps, in-memory caches you run yourself
I / D (storage)Fast or dense local disksLocal NoSQL scratch, HDFS — not durable databases of record
G / P / InfGPU or acceleratorsML, video, graphics

Graviton types end in g after the generation (m7g, c7g, t4g). They are AWS Arm CPUs. For Linux workloads that are not locked to x86 licenses, Graviton is often the cost/performance answer.

T-series CPU credits work for bursty load. Sustained high CPU under an Auto Scaling target means you wanted M or C — not Unlimited T forever as a silent bill.

Purchase options — how you pay (high level for SAA)

Three ideas cover most stems. The rest are edge cases.

OptionIn plain EnglishExam reflex
On-DemandList price, no commitment, no interruptionUnknown load, or the HA floor in a mixed ASG
Savings PlansCommit to $/hour for 1 or 3 years; discount applies automaticallySteady spend; Compute SP also covers Fargate/Lambda flexibility
SpotSpare capacity, deep discount; AWS can reclaim (~2 minute notice)Stateless fleets, batch with checkpoints, mixed with On-Demand

Reserved Instances still appear: Standard RI ≈ maximum discount on a known shape; Convertible RI ≈ discount with exchange rights. For SAA, if the stem wants flexibility across families or Lambda too, prefer Compute Savings Plans over a locked Standard RI.

Dedicated Hosts — physical server visibility for per-socket licenses (Windows/SQL/Oracle). Capacity Reservations guarantee On-Demand capacity in an AZ; they do not discount by themselves.

Placement groups — latency versus blast radius

A placement group asks the scheduler where instances may land. It is not Multi-AZ HA by itself.

flowchart LR cluster[Cluster] --> sameAZ[Same_AZ_low_latency] spread[Spread] --> racks[Distinct_hardware_max_7_per_AZ] partition[Partition] --> hadoop[Replica_aware_big_data]

Follows Placement groups. Cluster = performance; spread = small critical fleets; partition = Hadoop/Cassandra-style replica isolation.

Cluster — pack close (same AZ) for lowest latency / HPC. Shared failure domain. Never the HA answer for a web tier.

Spread — distinct hardware; AWS documents up to seven running instances per AZ. Good for a few critical nodes across AZs; wrong for a 50-node Hadoop fleet.

Partition — groups of racks with a partition index. The big-data answer when software places replicas apart.

Stop, terminate, hibernate

Stop keeps EBS, clears RAM, and usually drops the public IPv4 (unless you use an Elastic IP). Terminate deletes the instance (root volume often goes with it). Hibernate writes RAM to the encrypted root EBS so start resumes warm state. Hibernate needs an encrypted root large enough for RAM — it is not a backup and not Multi-AZ.

Use case 1 — stateless web API, cheap and highly available

Need: Survive AZ loss, cut cost, little ops for replacements.

Design: Application Load Balancer + Auto Scaling group in 2+ AZs. Launch template with Graviton general-purpose types. Mixed instances: On-Demand floor + Spot for peaks. Compute Savings Plan on the daytime baseline.

flowchart LR user[Users] --> alb[ALB] alb --> asg[ASG_2plus_AZs] asg --> od[OnDemand_floor] asg --> spot[Spot_peak]

Use case 2 — tightly coupled HPC

Need: Lowest node-to-node latency for MPI.

Design: Cluster placement group in one AZ, compute or HPC family, often Elastic Fabric Adapter (EFA). Not Multi-AZ — you traded blast radius for speed.

flowchart LR nodes[EC2_nodes] --> cluster[Cluster_placement] cluster --> efa[EFA_MPI]

Use case 3 — resume a long warm-up overnight

Need: Models take 25 minutes to load into RAM; pause at night without a cold boot.

Design: Encrypted EBS root sized for RAM + OS, hibernate on a supported family. Stop alone loses RAM; snapshots do not capture RAM.

Case study 1 — cost, HA, Linux web tier

Stem

A stateless HTTPS API on Amazon Linux. Daytime traffic is steady; evenings triple for four hours. Must survive AZ failure, stay cost-effective, and replace unhealthy instances without tickets. What meets the requirements?

A — wrong One On-Demand m6i.8xlarge in a single AZ with an Elastic IP and a page for a human to launch a second instance.
B — wrong Auto Scaling of T-family, all Spot, one AZ, Standard RIs for t3.xlarge.
C — correct ALB + ASG across 2+ AZs, Graviton types, On-Demand floor + Spot for the peak, Compute Savings Plan on the daytime baseline.
D — wrong Cluster placement of C-family behind an NLB in one AZ “for performance.”

A is a single point of failure. B fails AZ, sustained CPU on T, and all-Spot with no floor. D optimizes inter-node latency the API does not need and fails HA. C is the default SAA web pattern.

Case study 2 — hibernate prerequisites

Stem

A simulation engine takes 25 minutes to load models into RAM. Analysts pause overnight but need models still in memory in the morning. Root volume is unencrypted gp3 today. What works?

A — wrong Stop at night and start in the morning on a larger type so the OS boots faster.
B — correct Encrypt the root (copy AMI/volume), size it for RAM + OS, enable hibernation on a supported family, hibernate overnight.
C — wrong Snapshot each evening and restore a new instance at 08:00.
D — wrong Move the engine to Lambda with models in the deployment package.

Stop and snapshots discard or never capture RAM. Lambda’s time and size limits do not fit. Hibernate requires an encrypted root with enough space — that is B.

Case study 3 — placement for HDFS

Stem

HDFS on EC2 must place replicas so one rack failure does not lose two copies of the same block. The cluster will exceed 50 data nodes. Which placement fits?

A — wrong One cluster placement group for all nodes.
B — wrong Spread across three AZs so every node is unique hardware.
C — correct Partition placement group; configure HDFS rack awareness with the partition index.
D — wrong No placement group; pin each node to Dedicated Hosts in a spreadsheet.

Cluster shares fate. Spread’s seven-per-AZ cap cannot hold 50 nodes. Partition is the documented big-data pattern.

Tricky points (still explained simply)

User data is bootstrap, not a CM platform. Bake a golden AMI; keep user data short. Compiling from source on every scale-out is the wrong “fast launch” answer.

AMI IDs do not cross Regions. Copy them (and the KMS key story) for DR.

Spot can be reclaimed. Plan for the ~2 minute notice. Never put the only copy of critical state on one Spot node. Mix Spot with an On-Demand floor.

Hibernate ≠ stop ≠ snapshot. Hibernate keeps RAM (encrypted root). Stop keeps EBS only. Snapshot backs up EBS for later restore — no RAM.

IMDSv2 — require a session token; use hop limit 1 to reduce SSRF risk from containers. Role credentials come from IMDS; app secrets come from Secrets Manager / SSM.

Cluster placement is one AZ — performance, not HA. Spread is small fleets. Partition is replica-aware scale.

Light touch on the exam Every instance generation letter, RI Marketplace trading bots, deep EFA tuning. Know the names; do not deep-dive.
