CloudWatch and CloudTrail — is it healthy, and who touched it?

Must-knowDomains 1 & 2 · monitor vs audit

CloudWatch answers “how is this resource doing?” with metrics, logs, and alarms. CloudTrail answers “who did what, when?” with an API audit history. On the exam those two questions must not get mixed up.

Start here — the W questions

Why

Without metrics you scale late and debug blind. Without an audit trail you cannot prove who deleted a bucket or opened a security group. Operations and compliance both need evidence — different kinds.

What

Amazon CloudWatch collects metrics, stores logs, fires alarms, and can run synthetic checks. AWS CloudTrail records API activity (management events by default; data events optional). X-Ray traces requests across services when the stem is distributed latency.

Where

Metrics and log groups are Regional (dashboards can show many Regions). CloudTrail can be a multi-Region or organization trail delivering files to an S3 bucket you choose.

Which pieces matter

Metric vs log · alarm actions · CloudWatch Agent (memory!) · Logs Insights · subscription filters · trail to S3 · management vs data events · CloudWatch vs CloudTrail fork.

Core knowledge (beginner foundations)

Two different questions

Performance: “Is CPU above 80%?” → CloudWatch metric + alarm. Audit: “Who terminated that instance?” → CloudTrail event. Same console family in people’s heads; different services on the exam.

Metric — a number over time (CPUUtilization, request count). Default EC2 metrics do not include memory or disk used — install the CloudWatch Agent (or push a custom metric).

Alarm — watches a metric (or math/composite) and can notify SNS, scale an ASG, or stop/reboot/recover an instance.

Log group / stream — containers for log events. Lambda and many AWS services send logs here automatically; EC2 needs the agent.

Trail — configuration that delivers CloudTrail events to S3 (and optionally CloudWatch Logs) for retention beyond the console’s default history.

How monitoring and audit fit together (from AWS docs)

flowchart LR app[App_or_AWS_service] --> metrics[CloudWatch_metrics] app --> logs[CloudWatch_Logs] metrics --> alarm[Alarm] alarm --> sns[SNS_or_ASG] api[API_calls] --> trail[CloudTrail] trail --> s3[S3_audit_bucket]

Conceptual split. See What is Amazon CloudWatch? and What is AWS CloudTrail?.

CloudWatch — metrics, logs, alarms

Default EC2 metrics arrive every 5 minutes (1 minute with detailed monitoring). Custom metrics use PutMetricData. Metric filters turn log patterns (for example ERROR counts) into metrics you can alarm on.

Logs Insights runs queries against log groups. Subscription filters stream logs in near real time to Lambda, Kinesis, or Firehose (batch export to S3 is slower — different tool).

Synthetics canaries are scripts that hit your URL on a schedule — “is the homepage up from the outside?”

CloudTrail — management vs data events

TypeRecordsDefault
Management eventsControl plane (CreateBucket, RunInstances)On (console history ~90 days)
Data eventsData plane (S3 object-level, Lambda invoke)Off — extra cost; enable when needed
InsightsUnusual API activity patternsOptional

Use a multi-Region trail (or organization trail) to S3 for long-term, immutable-ish storage. Turn on log file integrity validation when the stem cares about tampering. Query with Athena on the S3 files, or CloudTrail Lake.

Use case 1 — scale on CPU, alert on errors

Need: ASG grows when busy; ops gets SMS when the app logs ERROR spikes.

Design: CloudWatch alarm on CPU → ASG policy. Agent or app logs → log group → metric filter on ERROR → alarm → SNS.

Use case 2 — compliance audit store

Need: Keep API history for years; prove who changed IAM.

Design: Organization trail → central S3 bucket with Object Lock / restricted access. Optional CloudWatch Logs for recent search.

Use case 3 — memory-based scaling

Need: Scale when RAM is high. Default metrics are not enough.

Design: CloudWatch Agent custom memory metric → alarm → ASG. Do not pick “enable detailed monitoring” alone — that only shortens the interval for default metrics.

Case study 1 — who terminated?

Stem

An instance disappeared. Security asks which IAM principal called TerminateInstances yesterday.

A — wrong CloudWatch CPU graphs. They show load, not identity.
B — correct CloudTrail event history (or the trail’s S3 logs / Athena).
C — wrong VPC Flow Logs alone — they show IP traffic, not the AWS API caller.
D — wrong Config recorder without CloudTrail — Config knows configuration state, not the full API “who.”

Case study 2 — memory alarm

Stem

Scale the ASG when memory exceeds 70%. Instances already have detailed monitoring enabled.

A — wrong Alarm on the default MemoryUtilization metric — it does not exist by default.
B — correct Install CloudWatch Agent, publish memory metric, alarm → ASG.
C — wrong CloudTrail Insights on RunInstances.
D — wrong Only enable Synthetics canaries.

Case study 3 — long-term API logs

Stem

Auditors need seven years of management API history across all Regions, queryable with SQL.

A — wrong Rely on the console’s 90-day Event history only.
B — correct Multi-Region (or org) trail to S3, then Athena (or CloudTrail Lake).
C — wrong CloudWatch metrics retention settings.
D — wrong Enable only S3 data events and skip management events.

Tricky points (still explained simply)

Detailed monitoring ≠ memory. It changes default metric frequency, not which OS metrics exist.

CloudTrail is not a performance dashboard. High API volume Insights ≠ “CPU is hot.”

Export vs subscribe. Batch export to S3 can lag hours. Near real-time needs a subscription filter.

EventBridge can react to CloudWatch alarm state changes and many AWS events — useful glue, not a replacement for trails or metrics.
