Hybrid networking — VPN, Direct Connect, Transit Gateway, endpoints

Must-knowDomains 1–3 · connect offices, hubs, private AWS APIs

Most apps live in a VPC. Hybrid networking is how that VPC talks to your office, other VPCs, and AWS public services without screaming across the open internet when you do not want to. On the exam you match “need it today,” “dedicated bandwidth,” “many VPCs,” and “private S3” to the right building block.

Start here — the W questions

Why

Offices and datacenters still hold data and users. Peering every VPC to every other VPC becomes a mesh nightmare. Some compliance rules forbid NAT to the public internet just to reach S3.

What

A toolbox: Site-to-Site VPN (encrypted over the internet), Direct Connect (dedicated private fiber), Transit Gateway (hub for many VPCs/VPNs), VPC endpoints / PrivateLink (private path to AWS or your services), plus newer names like Network Firewall and Lattice.

Where

VPN and DX attach to your Region (VGW, DX Gateway, or Transit Gateway). Endpoints live in your VPC subnets. Traffic can stay on the AWS backbone or your DX circuit instead of the public internet.

Which pieces matter

VPN vs DX · DX VIF types · Transit Gateway · gateway vs interface endpoint · PrivateLink · DX + VPN backup. Those ideas cover most hybrid stems.

Core knowledge (beginner foundations)

Internet VPN vs dedicated fiber

Site-to-Site VPN builds IPsec tunnels over the public internet in minutes. Performance varies. Direct Connect (DX) is a physical connection at a DX location into AWS — consistent bandwidth, weeks to provision, not encrypted by default (add VPN on top if you need encryption).

Customer gateway (CGW) — your on-premises VPN device (or software).

Virtual private gateway (VGW) — the AWS side of a VPN attached to one VPC (or use Transit Gateway instead for many VPCs).

Transit Gateway (TGW) — a Regional hub. Attach VPCs, VPNs, and DX (via transit VIF). Attachments get routes; you avoid a full mesh of peering.

VPC endpoint — private connectivity to an AWS service. Gateway endpoint (S3, DynamoDB) is free route-table magic. Interface endpoint (PrivateLink) is an ENI in your subnet for most other services.

Direct Connect VIFs — three doors

VIFIn plain EnglishTypical use
PrivateReach private IPs in a VPC (via VGW)One or few VPCs
TransitReach many VPCs through Transit GatewayHub architecture
PublicReach AWS public service endpoints over DXS3 over DX without VPC endpoint (older pattern)

DX Gateway lets one DX connect into VPCs (or TGWs) across Regions. For HA, use two DX locations; often keep a VPN as backup while DX is primary.

Gateway endpoint vs interface endpoint

Need private S3 or DynamoDB from a VPC with no internet gateway? Prefer a gateway endpoint — add a prefix list route; no hourly ENI charge. Need private access to KMS, Secrets Manager, ECR, API Gateway execute-api, or a service you expose? That is an interface endpoint (PrivateLink).

PrivateLink also lets you publish your own NLB-backed service so other accounts consume it without VPC peering or exposing the internet.

Remember “Need connectivity this afternoon” → VPN. “Consistent dedicated bandwidth” → DX. “Encrypt over DX” → VPN on top of DX. “Many VPCs, one hub” → Transit Gateway.

Use case 1 — quick hybrid for a pilot

Need: Office must reach one VPC this week; encryption required; bandwidth is modest.

Design: Site-to-Site VPN: CGW + VGW (or TGW), two tunnels, routes on both sides. Optional Accelerated VPN (Global Accelerator under the hood) if the stem stresses internet path quality.

Use case 2 — enterprise hub

Need: Dozens of VPCs, DX from HQ, branch VPNs, shared services VPC.

Design: Transit Gateway + transit VIF from DX + VPN attachments. Route tables on TGW isolate prod from sandbox if required.

flowchart TD hq[HQ_via_DX] --> tgw[Transit_Gateway] branch[Branch_VPN] --> tgw tgw --> prod[Prod_VPCs] tgw --> shared[Shared_services_VPC]

Use case 3 — private S3, no NAT

Need: Private subnets must read S3; no NAT Gateway cost; no public IP.

Design: S3 gateway endpoint on the route tables. For ECR pull + Secrets Manager, add interface endpoints.

Case study 1 — VPN now, DX later

Stem

A company must connect the datacenter to a VPC within days for encrypted traffic. Later they will add dedicated bandwidth. What first?

A — correct Site-to-Site VPN now. Plan DX as the later primary path; keep VPN as backup.
B — wrong Only Direct Connect — provisioning takes weeks.
C — wrong Public internet with open security groups.
D — wrong VPC peering to the datacenter — peering is VPC-to-VPC, not to on-premises.

Case study 2 — hub vs peering

Stem

Twenty application VPCs must reach a shared services VPC and each other selectively. Peering mesh is unmanageable.

A — wrong Full mesh peering and manual route updates forever.
B — correct Transit Gateway with separate route tables for isolation.
C — wrong One giant flat VPC for all teams.
D — wrong CloudFront between VPCs.

Case study 3 — endpoints

Stem

EC2 in private subnets must use S3 and Secrets Manager. No internet gateway. Least cost for S3.

A — wrong NAT Gateway for everything — works but costs egress and is not “private AWS backbone only.”
B — correct S3 gateway endpoint + interface endpoint for Secrets Manager.
C — wrong Interface endpoint for S3 only (possible, but gateway is the usual least-cost S3 answer).
D — wrong Public subnet with public IPs and a deny-list.

Tricky points (still explained simply)

DX is not encrypted by default. Add IPsec (VPN) when the stem requires encryption.

Peering ≠ Transit Gateway. Peering is one-to-one and does not transitive-route through a third VPC. TGW does hub routing.

Gateway endpoints only for S3 and DynamoDB. Almost everything else is interface/PrivateLink.

Name-level extras: Network Firewall (DNS/HTTP filtering in VPC), VPC Lattice (service-to-service), VPC IPAM (CIDR inventory). Know the job; do not deep-dive.

Light touch on the exam BGP community details, LAG math, Lattice auth policy syntax, Network Firewall rule-group JSON.
