Amazon VPC — the private network your apps live in

Must-knowDomain 1 · Secure · Domain 2 · Resilient · Domain 3

A VPC is your private network inside an AWS Region. Subnets, route tables, gateways, and firewalls decide who can talk to whom. On the exam you place workloads across Availability Zones, keep databases private, and pick the cheapest path that still meets every security and HA constraint.

Start here — the W questions

Why

Cloud servers need IP addresses, routes, and firewalls — just like an office datacenter — but shared with millions of other customers. You need a logically isolated network so your app is not on the open internet by default.

What

An Amazon VPC (Virtual Private Cloud) is a Regional, logically isolated virtual network. You carve it into subnets, attach route tables, and control traffic with security groups and optional network ACLs. Internet access uses an internet gateway or a NAT Gateway; private AWS API access often uses VPC endpoints.

Where

A VPC spans one Region (all AZs in that Region). Each subnet sits in exactly one Availability Zone. An ENI, NAT Gateway, or EBS volume in that subnet is AZ-bound. Multi-AZ HA means resources in more than one subnet/AZ.

Which pieces matter

Subnet + route table · IGW vs NAT · security group vs NACL · gateway vs interface endpoint · peering vs Transit Gateway · Multi-AZ placement. Those ideas cover almost every SAA VPC question.

Core knowledge (beginner foundations)

Public vs private — it is the route table

A public subnet is a subnet whose route table sends 0.0.0.0/0 to an internet gateway (IGW). A private subnet has no route to an IGW. Auto-assign public IP is a convenience, not the definition. Read the route table — not the subnet’s display name.

CIDR — the IPv4 address range of the VPC (between /16 and /28). Subnets carve slices of that range. Overlapping CIDRs block VPC peering.

Five reserved addresses — AWS keeps five IPs in every subnet (network, router, DNS, future use, broadcast). A /24 gives 251 usable addresses, not 256.

ENI — Elastic Network Interface, the virtual network card on an instance, load balancer node, or interface endpoint. Security groups attach to ENIs.

How a packet moves (from AWS docs)

Traffic hits the subnet’s network ACL first, then the ENI’s security group. Outbound, a stateful security group remembers the connection; a stateless NACL needs matching return (ephemeral) rules.

Security group vs network ACL

A security group attaches to an ENI. It is stateful: allow inbound 443 and return traffic is allowed automatically. Rules are allow-only — you cannot write a deny. Prefer referencing another security group as a source (“app SG may reach db SG on 5432”) so Auto Scaling IP changes do not break you.

A network ACL (NACL) attaches to a subnet. It is stateless: inbound allow does not open the return path. You must also allow ephemeral ports (often 1024–65535) outbound. Rules are numbered; first match wins; explicit DENY exists. “Block this one attacker IP for every instance in the subnet” is a NACL answer. Security groups cannot deny.

Default NACL allows all traffic. Custom NACLs start closed. If someone “opened the security group and it still fails,” think NACL ephemeral ports, missing routes, or missing public IPs — not a security-group deny.

Internet path, NAT, and endpoints

An internet gateway is Regional and highly available. One IGW per VPC. You do not build two for HA.

A NAT Gateway sits in a public subnet with an Elastic IP. Private subnets send default traffic to it for outbound IPv4 without inbound reachability. NAT is AZ-bound: for Multi-AZ outbound HA, place one NAT per AZ and point each private subnet at its local NAT. NAT Gateways have no security groups. Prefer NAT Gateway over a NAT instance unless the stem wants a security group on the NAT.

Gateway endpoints (free) exist for S3 and DynamoDB only. They update route tables. Interface endpoints (PrivateLink) create ENIs, cost money, and cover most other AWS APIs — and optional S3 when on-premises needs a private IP.

IPv6 outbound-only uses an egress-only internet gateway, not a NAT Gateway.

Peering vs Transit Gateway

VPC peering connects two VPCs. It is not transitive: A↔Shared and B↔Shared does not give A↔B. CIDRs must not overlap. You must add routes both ways.

When many VPCs (and maybe on-premises) must talk, use a transit gateway — a Regional hub with transitive routing according to the TGW route tables you write. There is no “enable transitive peering” checkbox.

Use case 1 — three-tier web app, Multi-AZ

Need: Internet users hit HTTPS; app and database stay private; survive one AZ failure.

Design: Public subnets: ALB only. Private: app ASG. More-private: RDS. Security groups chained ALB → app → db. NAT per AZ if the app needs outbound patches. No IGW route on the database subnet.

flowchart LR user[Users] --> alb[ALB_public] alb --> app[App_ASG_private] app --> db[RDS_private]

Use case 2 — private S3 without NAT cost

Need: Private EC2 must use S3 and DynamoDB in the same Region; minimize cost.

Design: Gateway endpoints on the private route tables. Use interface endpoints for Secrets Manager, ECR, SSM, and similar — there is no gateway endpoint for those.

flowchart LR ec2[Private_EC2] --> gw[Gateway_endpoint] gw --> s3[S3_or_DynamoDB]

Use case 3 — operators without opening SSH to the world

Need: Reach private Linux instances; no inbound port 22 from the internet.

Design: SSM Session Manager with an instance profile and a path to SSM endpoints (NAT or interface endpoints for ssm, ssmmessages, ec2messages). A locked-down bastion is the older pattern.

Case study 1 — NAT placement is an HA question

Stem

App instances in private subnets in us-east-1a and us-east-1b must pull OS patches from the internet. Design must still patch if an AZ fails. S3 traffic in us-east-1 must not traverse the internet and should minimize cost.

A — wrong One NAT in us-east-1a for both private route tables; S3 via that NAT.
B — wrong One NAT per AZ, plus an interface endpoint for S3 in both AZs.
C — correct One NAT per AZ (each private subnet → local NAT) plus a gateway VPC endpoint for S3.
D — wrong No NAT; gateway endpoints for S3 and “for the internet.”

A fails AZ HA and bills S3 through NAT. B meets HA but pays for PrivateLink S3. D invents a gateway endpoint for the internet. C is Multi-AZ for patches and free for same-Region S3.

Case study 2 — the firewall that can say no

Stem

Security wants one hostile /32 blocked at the subnet boundary for every instance, including future ENIs. Instances already allow only the ALB via security groups. After a contractor added a custom NACL allowing inbound 443, some legitimate clients stall during the handshake.

A — wrong Add a deny for the /32 on the instances’ security group.
B — wrong Move instances to a public subnet so they share one NACL with the ALB.
C — correct Low-numbered NACL DENY for that /32; keep SG allow-list from the ALB; add ephemeral port ALLOWs so the stateless NACL does not drop return traffic.
D — wrong Enable Flow Logs and rely on GuardDuty to block the IP automatically.

Security groups cannot deny. D is detective, not preventive. C uses the only VPC deny primitive and fixes the forgotten ephemeral ports that caused handshake stalls.

Case study 3 — peering is a pair, not a hub

Stem

Three VPCs: Shared, AppA, AppB. AppA and AppB are each peered with Shared. Apps in AppA must open TCP to AppB. More app VPCs will arrive; the team does not want a full mesh.

A — wrong Enable transitive peering on Shared so AppA hairpins to AppB.
B — wrong Add routes in AppA/AppB for each other’s CIDR targeting the Shared peering.
C — correct Attach all three VPCs to a transit gateway and route spoke-to-spoke on TGW route tables.
D — wrong NAT Gateway in Shared and default-route AppA and AppB through it.

Transitive peering does not exist. Routes through Shared do not make Shared a router for third-party CIDRs. C is the documented hub-and-spoke that still works at the tenth VPC.

Tricky points (still explained simply)

Public is a route, not a label. You need IGW attached, route to the IGW, and a public/Elastic IP on the ENI for inbound/outbound via the IGW. NAT is how private instances get outbound IPv4 without a public IP on the instance.

NAT Gateway is AZ-bound, billed, and IPv4. Do not send S3/DynamoDB through it when a gateway endpoint works. Do not put it in a private subnet. Do not attach a security group to it.

Security groups = stateful, ENI, allow-only. NACLs = stateless, subnet, allow and deny. Ephemeral-port bugs are NACL-only. “Deny this IP” is NACL (or WAF/Network Firewall when the stem is HTTP).

Gateway endpoints: S3 and DynamoDB, free, same Region. No gateway endpoint for SSM, STS, ECR, Secrets Manager, KMS, or “the internet.”

Flow Logs are not Wireshark. They show accept/reject metadata, not payloads. They omit IMDS, Amazon DNS, DHCP, and similar metadata-path traffic.

Multi-AZ is HA, not DR. Two AZs survive an AZ outage. Regional failure needs a second Region (or defined on-premises fallback) plus failover DNS or similar.

Exam habit Draw the route table before the security group. Satisfy HA first, then replace NAT-to-S3 with a gateway endpoint so you get both resilience and cost.
