Elastic Load Balancing and Auto Scaling — many servers, one door

Must-knowDomains 2 & 3 · Resilient · Performance

A load balancer gives users one address while many instances come and go. Auto Scaling grows, shrinks, and replaces those instances. Together they are the default highly available EC2 pattern on SAA-C03 — if you pick the right load balancer and let its health checks drive the group.

Start here — the W questions

Why

One server dies, gets slow, or sits in one AZ. Users should not notice. You need a front door that skips unhealthy targets, and a control loop that adds or removes servers without a ticket.

What

Elastic Load Balancing (ELB) spreads traffic across targets. EC2 Auto Scaling keeps a fleet at the right size using a launch template. You pay for the balancers and instances; the Auto Scaling control plane itself has no separate “ASG fee.”

Where

Load balancers live in subnets you choose (public for internet-facing, private for internal). Auto Scaling launches instances into the AZs those subnets cover. Health and scale decisions are Regional for the service, but each instance still sits in one AZ.

Which pieces matter

ALB vs NLB vs Gateway Load Balancer · target group · listener rules · ASG min/desired/max · launch template · ELB health checks · scaling policies. Classic Load Balancer is legacy — almost never a green-field answer.

Core knowledge (beginner foundations)

The request path in one breath

A client hits a load balancer DNS name. A listener matches protocol and port (and maybe host or path). Traffic goes to a target group. The target group health-checks each target. Unhealthy targets stop getting new work. Auto Scaling registers new instances with that target group when you attach them.

Internet-facing vs internal — public balancer in public subnets with a route to an internet gateway; internal balancer has only private IPs for tier-to-tier traffic inside the VPC.

Target types — instances, IP addresses, Lambda (ALB), or another load balancer in some designs. One target group does not mix instance and Lambda.

Deregistration delay (connection draining) — when a target leaves, existing requests can finish for a grace period (often default 300 seconds) while new requests go elsewhere.

Cross-zone load balancing — each balancer node can send to healthy targets in every AZ so uneven instance counts still get even load. ALB defaults on; know the idea for NLB stems where one AZ has fewer targets.

How traffic and scaling work together (from AWS docs)

AWS’s mental model: clients → load balancer → healthy targets; Auto Scaling changes desired capacity from policies, then waits for launch, warmup, and health before counting an instance as in service.

Combines the ELB target-group model in What is an Application Load Balancer? with What is Amazon EC2 Auto Scaling?. Open those pages for AWS’s official overviews.

Stems often sound like networking. The balancer type is the answer. Memorize one sentence each.

flowchart TD q{{What does the question need}} q -->|HTTP path or host or WAF| alb[ALB] q -->|static IP or UDP or PrivateLink| nlb[NLB] q -->|inline firewall fleet| gwlb[GWLB] q -->|path plus static IP| both[NLB_in_front_of_ALB]

Product choice overview. Compare features in What is Elastic Load Balancing?.

ALB — terminate TLS with ACM, attach WAF, route /api to one target group and /static to another. Can invoke Lambda as a target for simple HTTPS fronts.

NLB — partner firewalls allowlist Elastic IPs that do not change as you scale. UDP lives here. WAF does not attach directly to NLB (use ALB or CloudFront for WAF).

GWLB — not “another HTTP balancer.” Route tables send traffic to a GWLB endpoint; appliances see original packets over GENEVE. Wrong tool for ordinary websites.

Listeners, stickiness, and TLS

TLS usually ends at the balancer with an ACM certificate (least ops). End-to-end TLS means HTTPS to the instance with a cert you manage. If the instance must see the client certificate, think NLB TLS pass-through or TCP — not normal ALB termination.

Stickiness (session affinity) pins a client to one target. It papers over sessions stored in process memory. Prefer sessions in ElastiCache, DynamoDB, or a JWT. Stickiness is not high availability — if that target dies, those sessions still die.

Auto Scaling — size, health, and cost

You set minimum, desired, and maximum capacity. A launch template (not the old launch configuration) versions AMI, type, security groups, user data, and IAM profile. Mixed instances policies combine On-Demand and Spot across several types so one Spot pool drying up does not take the service down.

flowchart LR metric[CPU_or_ALB_requests] --> track[Target_tracking] track --> desired[Desired_capacity] desired --> launch[Launch_template] launch --> warm[Warmup] warm --> elb[ELB_health_check] elb --> ok[InService] fail[Failed_health] --> replace[Replace_instance]

Follows scaling and health concepts in Target tracking scaling and Use Elastic Load Balancing health checks.

Scaling policies: Target tracking (“keep CPU at 50%” or “ALB requests per target at 1000”) is the default. Step scaling for non-linear jumps. Scheduled for known rush hours. Predictive when history shows a daily pattern and reactive scale-out is always late.

Health is a contract. EC2 status checks catch a dead host. They do not catch “nginx returns 502.” Attach the target group and enable ELB health checks on the ASG so a failing /health is replaced. Set the health check grace period longer than app boot or you kill slow starters. Lifecycle hooks give almost-stateless apps time to drain before terminate.

Use case 1 — HTTP microservices with WAF

Need: Host and path routing, WAF, Multi-AZ, least ops.

Design: One internet-facing ALB, listener rules by host/path, WAF on the ALB (or CloudFront then ALB), ASG in private subnets across 2+ AZs, ELB health checks, deregistration delay.

flowchart LR user[User] --> alb[ALB_plus_WAF] alb -->|path_api| asg[ASG_EC2] alb -->|path_hooks| lambda[Lambda_target]

Use case 2 — partner needs allowlisted IPs

Need: TCP or UDP, static IPs, huge connection count.

Design: NLB with Elastic IPs per AZ. If you also need HTTP path routing, put NLB in front of ALB.

flowchart LR partner[Partner_allowlist] --> nlb[NLB_Elastic_IPs] nlb --> alb[ALB_optional] alb --> targets[Targets]

Use case 3 — inspect all VPC traffic with appliances

Need: Third-party firewall or IDS inline, without rewriting apps.

Design: Gateway Load Balancer + appliance Auto Scaling group; route tables send traffic to GWLB endpoints.

flowchart LR src[Source_subnet] --> ep[GWLB_endpoint] ep --> gwlb[GWLB] gwlb --> fw[Firewall_ASG]

Case study 1 — HTTP routing, WAF, Lambda target

Stem

app.example.com is public. /api/* goes to an ASG of EC2 in private subnets. /hooks is a low-traffic function with no servers. Need WAF, survive AZ failure, keep ops light. Most cost-effective design?

A — wrong NLB with TCP. Attach WAF to the NLB. Register ASG and Lambda on one NLB target group.
B — correct ALB with path rules: /api/* → ASG target group, /hooks → Lambda target group. WAF on the ALB. ASG in 2+ AZs with ELB health checks.
C — wrong Two Classic Load Balancers and manual instance registration.
D — wrong GWLB in front of EC2 because “security inspection.”

WAF attaches to ALB/CloudFront, not NLB. NLB does not do path routing or Lambda targets the ALB way. GWLB is for appliance fleets, not HTTP path rules. B matches ALB’s job.

Case study 2 — static IP and UDP

Stem

A game server uses UDP. A partner firewall must allowlist fixed IPs. Connection rates are extreme. Path-based HTTP routing is not required. What do you use?

A — wrong ALB with HTTPS listeners and WAF.
B — correct NLB with UDP listeners and Elastic IPs per AZ.
C — wrong GWLB because games need “gateways.”
D — wrong Classic Load Balancer with sticky sessions.

ALB is HTTP-family only. GWLB is appliance steering. NLB is the UDP + static IP answer.

Case study 3 — unhealthy app, healthy EC2

Stem

An ASG sits behind an ALB. Instances pass EC2 status checks but return HTTP 500 on /health. Users keep hitting bad nodes. Desired capacity never changes. What is missing?

A — wrong Switch to a cluster placement group.
B — wrong Replace the ALB with an NLB so health checks become “stronger.”
C — correct Configure the ASG to use ELB health checks so failing target-group health replaces the instance.
D — wrong Disable deregistration delay so bad nodes leave faster.

EC2 checks do not see application 500s. ELB health on the ASG is the fix. NLB does not magically fix HTTP health semantics. Draining affects leave behavior, not detection.

Tricky points (still explained simply)

ALB ≠ NLB ≠ GWLB. Layer 7 HTTP features, Layer 4 static IP/UDP, and inline appliances are three different jobs.

ELB health vs EC2 health. Without ELB health on the ASG, a process crash that still pings the hypervisor looks “healthy.”

Stickiness is a crutch. Prefer external session state. Sticky + one sticky target dying still loses sessions.

Launch templates, not launch configs, for new designs — versioning and mixed On-Demand/Spot.

Grace period too short causes replace loops during slow boots. No deregistration delay drops in-flight requests on deploy.

PrivateLink endpoint services front with NLB in the provider VPC (ALB can sit behind that NLB if you need L7).
