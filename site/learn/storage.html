Block and file storage — EBS, EFS, FSx, and hybrid tools

Must-knowDomains 2–4 · resilient, performance, cost

S3 is object storage. This chapter is the rest: disks you attach to one EC2 instance, file systems many instances mount together, Windows and HPC specialists, and tools that move or present data between a data center and AWS. On the exam, circle the OS, the protocol, and whether data may vanish — then pick the service.

Start here — the W questions

Why

Apps need different shapes of storage. A database wants a fast exclusive disk. A web fleet wants one shared folder. A Windows shop wants SMB and Active Directory. One product cannot do all of that well.

What

EBS is a network disk for one EC2 (usually) in one AZ. EFS is a shared Linux NFS file system across AZs. FSx is managed file systems for Windows (SMB), Lustre (HPC), and a few specialists. Storage Gateway, DataSync, and Snow connect on-premises to AWS.

Where

EBS volumes live in one AZ. EFS (Regional) is Multi-AZ in a Region. Snapshots of EBS are regional (stored in S3 behind the scenes) and can be copied to another Region. Hybrid tools sit in your data center and talk to AWS over the network — or travel by truck (Snow).

Which pieces matter

EBS vs instance store · gp3 vs io2 · EFS (Linux NFS) · FSx for Windows (SMB + AD) · FSx for Lustre · Gateway vs DataSync vs Snow. Those choices decide almost every storage stem.

Core knowledge (beginner foundations)

Block vs file in one breath

Block storage looks like a hard drive (you format it; one instance owns it). File storage looks like a shared folder (many computers mount the same path). EBS is block. EFS and FSx are file. S3 is object (not a POSIX disk) — still important because snapshots and many hybrid paths land in S3.

EBS volume — a durable disk in one AZ. Attach it to an EC2 in that same AZ. Survives stop/terminate if you keep the volume.

Instance store — disks on the physical host. Very fast. Ephemeral: stop, terminate, or lose the host and the data is gone.

Snapshot — a point-in-time backup of an EBS volume, kept in the Region (S3-backed). Create a new volume from it in another AZ or copy the snapshot to another Region for DR.

EFS — managed NFSv4 for Linux. Regional deployment = mount targets in multiple AZs; shared POSIX namespace.

FSx for Windows File Server — managed SMB/NTFS with Active Directory. FSx for Lustre — high-performance parallel file system for Linux HPC/ML, often linked to S3.

How to pick the storage family (decision from AWS docs)

Start from what the data must do: exclusive block disk, shared file system, or hybrid move/present. AWS documents each service around that job.

EBS and instance store

You create an EBS volume in one AZ and attach it only in that AZ. There is no “Multi-AZ EBS volume.” To move data to another AZ: snapshot → create volume in the target AZ. To another Region: copy the snapshot, then create a volume.

gp3 is the usual general-purpose SSD (boot disks and most apps). You can raise IOPS and throughput without making the disk huge. io2 is for sustained high provisioned IOPS (busy databases). st1 / sc1 are HDD for sequential or cold data — not boot volumes.

Multi-Attach (io1/io2 only) lets more than one Nitro instance in the same AZ attach the volume. The software on top must be cluster-aware. It is not a shared file system across AZs and not a substitute for EFS.

Encryption uses KMS. You cannot flip an existing unencrypted volume to encrypted in place. Documented path: snapshot → copy snapshot with encryption → new volume → swap.

flowchart LR unenc[Unencrypted_EBS] --> snap[Snapshot_still_unencrypted] snap --> copy[Copy_snapshot_with_KMS] copy --> encsnap[Encrypted_snapshot] encsnap --> newvol[New_encrypted_volume]

Follows Amazon EBS encryption. Default account encryption does not rewrite old volumes.

Instance store is the “highest IOPS, data can be rebuilt” answer. Anything that must survive a stop belongs on EBS, EFS, FSx, or S3.

EFS and FSx

EFS (Regional) is the Linux Multi-AZ shared folder. Mount from EC2, containers, or Lambda in the VPC. It is not a Windows file server and does not speak native SMB/AD the way FSx for Windows does. One Zone EFS is cheaper and dies with that AZ. Encryption at rest is KMS; TLS on the mount for in transit. EFS Replication to another Region is DR — Regional EFS itself is already HA inside the Region.

FSx for Windows File Server joins Active Directory, understands Windows ACLs, and serves SMB. Use it for Windows home directories and lift-and-shift Windows shares. Single-AZ or Multi-AZ.

FSx for Lustre is for HPC/ML scratch or persistent high throughput, often linked to an S3 data lake. Wrong for ordinary CMS home directories.

Hybrid: present, copy, or ship

Storage Gateway presents NFS/SMB (File), iSCSI (Volume), or a virtual tape library (Tape) while data lives in AWS (or snapshots to AWS). Ongoing hybrid access — not a one-shot migration tool.

DataSync copies over the network with checksums and schedules. Online migration or sync to S3, EFS, or FSx. Not a user-facing file share.

Snow ships a device when the network cannot finish in time. Data lands in S3; use lifecycle if you wanted Glacier classes. There is no “Snow directly into Glacier” path on the exam story.

Use case 1 — Linux web fleet, same files, two AZs

Need: Auto Scaling Amazon Linux in two AZs; every instance reads/writes the same upload tree; survive one AZ loss.

Design: Regional EFS, mount over NFS (TLS if required). Lifecycle cold files to IA. Not Multi-Attach EBS.

flowchart LR asg[ASG_two_AZs] --> efs[Regional_EFS]

Use case 2 — Windows share with AD

Need: Windows EC2 and desktops need SMB, NTFS ACLs, and existing Active Directory.

Design: FSx for Windows File Server joined to AD; Multi-AZ if HA was required. EFS is the wrong native answer.

Use case 3 — migrate vs present on-premises NFS

Need: Keep a live NFS mount for months while durable copies land in S3 for ML; network is usable.

Design: File Gateway (present) and/or DataSync (copy). Snow only if the pipe cannot finish before the deadline.

Case study 1 — shared files, two AZs, Linux

Stem

A CMS runs on Amazon Linux Auto Scaling in two AZs. Every instance must read and write the same upload directory. Files must survive instance replace and one AZ loss. Windows is not in use. Reasonable cost.

A — wrong io2 Multi-Attach to all instances.
B — wrong Instance store on each node plus cron rsync.
C — correct Regional EFS mounted over NFS; lifecycle toward IA for cold files.
D — wrong FSx for Windows Multi-AZ mounted with SMB on Linux.

Multi-Attach is same-AZ only and needs a cluster file system. Regional EFS is the documented Linux Multi-AZ share. See What is Amazon EFS?.

Case study 2 — encrypt EBS after the fact

Stem

Postgres on one EC2 has an unencrypted 2 TB gp3 volume in eu-west-1a. Compliance needs a customer-managed KMS key. Peak is 12,000 IOPS (gp3 is fine). Short planned cut-over is OK. Keep incremental backups.

A — wrong Enable default EBS encryption and reboot.
B — wrong Detach the volume, tick encrypt, reattach.
C — correct Snapshot → copy with CMK encryption → new volume in the same AZ → swap; continue snapshot backups of the new volume.
D — wrong Move the data directory to EFS for “free Multi-AZ.”

Case study 3 — present versus copy versus ship

Stem

A factory has 120 TB on NFS. Engineers must keep the NFS mount for six months. AWS needs a durable copy for SageMaker. 1 Gbps Direct Connect exists (partly used). Filer lease ends in eight months.

A — wrong Snowball this week, shut the filer, read from the S3 console.
B — wrong One DataSync run tonight, then mount S3 with a FUSE client.
C — correct File Gateway (and/or scheduled DataSync) so NFS stays available while objects land in S3; Snow only if the network cannot finish.
D — wrong Volume Gateway cached mode with iSCSI on the Linux workstations.

Tricky points (still explained simply)

EBS is AZ-locked; snapshots are regional. Mobility always goes through a snapshot (and copy for another Region).

Shared ≠ bigger EBS. Two AZs + same files = EFS (Linux) or FSx (Windows), not Multi-Attach.

Instance store is speed + a trap. Fastest local IOPS; zero durability across stop/terminate.

Gateway presents · DataSync copies · Snow ships. Do not mix those verbs.

Meet every constraint, then take the cheaper disk. gp3 before io2 when IOPS fit. One Zone EFS is cheaper and wrong if AZ loss was named.

Exam habit Circle OS, protocol, AZ/Region wording, and whether data may vanish. Those four circles usually leave one service.
