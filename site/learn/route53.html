Route 53 — give your app a name people can type

Must-knowDomains 2 & 3 · DNS, failover, latency

Route 53 is AWS’s DNS service. It turns a friendly name like example.com into the address of your website or API. On the exam you will use it to send users to healthy servers, to the closest Region, or to a backup site when the primary fails.

Start here — the W questions

Why

People type names, not IP addresses. Servers change IP addresses. Regions fail. You need a reliable phone book that can also say “if this Region is sick, send traffic to that one.”

What

Amazon Route 53 is a managed DNS (Domain Name System) service. AWS documents three jobs you can mix: register a domain, route traffic with DNS records, and health-check resources so unhealthy targets stop getting traffic.

Where

Route 53 is a global service. Its name servers sit at the edge of the internet. Your records live in a hosted zone (a container for one domain). Public zones answer the internet. Private zones answer only inside VPCs you attach.

Which pieces matter

Hosted zone · record · alias vs CNAME · routing policy · health check · private zone + Resolver (for hybrid). Those six ideas cover almost every SAA question.

Core knowledge (beginner foundations)

DNS in one breath

When you open www.example.com, your computer asks a DNS resolver: “What IP should I use?” The resolver asks Route 53 (if Route 53 is the authority for that domain). Route 53 looks up a record and returns an answer. Your browser then connects to that IP. DNS does not carry the web page — it only finds the door.

Domain name — the name you register (example.com). You can buy it in Route 53 or keep it at another registrar and still use Route 53 for DNS.

Hosted zone — the “folder” of DNS records for that domain. Same name as the domain. Public = internet. Private = only associated VPCs.

Record — one answer for one name. Example: “for www.example.com, send people to this load balancer.”

TTL (time to live) — how long resolvers may cache the answer. A high TTL means failover can feel slow, because some users keep the old answer. A low TTL updates faster but means more DNS queries (and cost).

How DNS traffic reaches your app (from AWS docs)

AWS walks through this as a numbered story: browser → ISP resolver → root → .com → Route 53 name server → your record → IP → your server. The Mermaid below follows that official flow.

Route 53’s three main functions, as AWS lists them:

  1. Domain registration — buy/renew a name.
  2. DNS routing — create records that point names at resources.
  3. Health checking — probe a resource; stop sending users there if it fails.

Alias vs CNAME (the first big “gotcha,” explained simply)

A normal CNAME record says “this name is another name.” Internet DNS rules say you cannot put a CNAME on the bare domain (the apex, like example.com), because that name already needs SOA and NS records.

An alias record is AWS’s solution. It looks like an A/AAAA record, can sit on the apex, and can point at AWS targets such as an ALB, CloudFront, S3 website endpoint, API Gateway, or another record in the same zone. Route 53 follows the target’s changing IPs for you. You never hard-code an ALB IP.

Remember Apex (example.com) → ALB / CloudFront / S3 website = alias. Never “CNAME the apex.” Subdomains to a non-AWS hostname often use a normal CNAME.

Routing policies — which answer should DNS give?

A routing policy is simply the rule Route 53 uses when more than one answer is possible. Read the stem; pick the policy that matches the sentence.

PolicyIn plain EnglishTypical stem
SimpleOne place (or a list of IPs with no fancy logic)Single website, no failover story
FailoverPrimary if healthy, else secondaryActive/passive DR between Regions
WeightedSend a percentage of users to BCanary, blue/green, gradual move
LatencySend to the AWS Region that is “closer” for this resolverBest performance across Regions
GeolocationSend by country/continent (plus a default)Laws, licensing, language sites
GeoproximityBias traffic toward a place; you can shift a sliderFine-tune between nearby stacks
MultivalueReturn several healthy IPs (simple DNS load sharing)A few servers, no load balancer yet

Decision view for SAA. Policy definitions: Choosing a routing policy.

Latency is not a law fence. It optimizes network distance to an AWS Region. If personal data must stay in Germany, that is geolocation (or an app-layer control), not latency.

Failover needs a health signal. Without a health check (or “evaluate target health” on an alias to an ELB/CloudFront), failover will not move traffic when something dies.

Use case 1 — simple public website

Need: Users type example.com and www.example.com, get HTTPS, content from S3, cached worldwide.

Design: CloudFront in front of S3. ACM certificate in us-east-1 for CloudFront. Route 53 alias A/AAAA records for apex and www → the distribution.

flowchart LR user[User] --> r53[Route53_alias] r53 --> cf[CloudFront] cf --> s3[S3_origin]

Use case 2 — active/passive disaster recovery

Need: If the primary Region’s API is unhealthy, send users to a secondary Region.

Design: Failover routing: primary + secondary records, health check (or evaluate target health on each Regional ALB), often a low TTL so caches expire faster. This is DNS failover — clients may still cache until TTL ends.

flowchart LR user[User] --> r53[Failover_policy] r53 -->|healthy| primary[ALB_Region_A] r53 -->|unhealthy| secondary[ALB_Region_B] hc[Health_check] --> r53

Detail: Configuring DNS failover.

Use case 3 — private names inside a VPC (and the office)

Need: payments.internal resolves to an internal ALB for EC2. The on-premises office must resolve the same name over Direct Connect/VPN. EC2 must also resolve legacy.corp.example that only exists on Windows DNS in the datacenter.

Design: Private hosted zone associated with the VPC. Route 53 Resolver inbound endpoints so on-premises can query AWS. Outbound endpoints + a forwarding rule so the VPC can query the Windows DNS.

Case study 1 — apex to CloudFront

Stem

You own example.com in a Route 53 public hosted zone. You want HTTPS for the apex and www, global caching, origin in S3. What works?

A — wrong CNAME at example.com to the CloudFront domain. CNAME is not allowed at the apex.
B — correct Alias A/AAAA for apex and www → CloudFront. ACM cert in us-east-1 covering both names.
C — wrong Paste CloudFront’s current IPs into apex A records. Those IPs change.
D — wrong Weighted S3 website endpoints and skip CloudFront “because alias cannot target CloudFront.” Alias to CloudFront at the apex is the normal pattern.

Alias exists specifically so apex names can target AWS resources. See alias vs non-alias.

Case study 2 — latency vs failover vs geo

Stem

An API runs in Tokyo and Ireland. Users should hit the Region with better network latency. If that Region’s ALB has no healthy targets, use the other Region. No data-residency law in the stem.

A — wrong Failover with Tokyo always primary. Irish users take a long path every day.
B — wrong Geolocation without a default. Wrong tool (no residency requirement) and some countries get no answer.
C — correct Latency-based records in both Regions, alias to each ALB, evaluate target health (or health checks).
D — wrong Simple routing listing both ALB names. No latency logic, no health removal.

Case study 3 — hybrid DNS

Stem

VPC apps resolve payments.internal to an internal ALB. On-premises hosts over Direct Connect need the same name. EC2 must resolve legacy.corp.example on Windows DNS in the datacenter.

A — wrong A “secret” public hosted zone. Still public DNS.
B — wrong Edit every hosts file. Does not scale.
C — correct Private hosted zone + Resolver inbound for the datacenter + outbound forward for corp.example.
D — wrong Geolocation public zone. Wrong problem.

Tricky points (still explained simply)

Alias ≠ generic internet feature. Other DNS hosts may not have “alias.” On Route 53, use it for AWS targets and apex.

Health checks from the internet cannot reach a private IP. For private ALBs, prefer alias + evaluate target health, or a CloudWatch-based check.

DNS failover is not instant. TTL caching remains. For minutes-scale RTO, lower TTL and have the secondary stack ready (pilot light / warm standby).

Split-horizon: same name in a public zone and a private zone — internet sees CloudFront; VPC sees the internal ALB. That is intentional.

Light touch on the exam Registrar transfers, WHOIS, Traffic Flow GUI details, Application Recovery Controller internals. Know the names; do not deep-dive.
