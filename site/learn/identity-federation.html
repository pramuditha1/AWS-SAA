Cognito, IAM Identity Center, and federation

Should-knowDomain 1 · Tasks 1.1–1.2

IAM users do not scale to a million mobile customers, and they are the wrong shape for employees who should open the AWS console with the same login they use for email. This chapter is the identity fork: Cognito for app users, IAM Identity Center for workforce SSO, and Directory Service / SAML when Windows or an external IdP is in the story.

Start here — the W questions

Why

Customers need sign-up, social login, and JWTs for your API. Employees need one portal into many AWS accounts. Windows servers need Active Directory. Mixing those three jobs breaks designs and fails easy exam items.

What

Amazon Cognito is for application users (customers). IAM Identity Center (successor to AWS SSO) is for workforce access to AWS accounts and business apps. AWS Directory Service provides Managed Microsoft AD or AD Connector for domain join. SAML/OIDC federation lets an external IdP (Okta, Entra ID) prove who someone is.

Where

Cognito user pools and identity pools are regional. Identity Center is an organization-wide control plane for many accounts. Directory Service runs domain controllers or connectors inside your VPC, often with VPN/Direct Connect back to on-premises AD.

Which pieces matter

Cognito user pool vs identity pool · IAM Identity Center permission sets · SAML federation to IAM roles · Managed Microsoft AD vs AD Connector. Those four forks cover almost every stem.

Core knowledge (beginner foundations)

Three audiences, three tools

App customers → Cognito. Employees into AWS → IAM Identity Center (or classic IAM SAML federation to roles). Windows domain join / Group Policy / FSx AD → Directory Service. None of these replace IAM roles; when AWS APIs are called, something still assumes a role and gets temporary credentials from STS.

User pool — Cognito’s managed directory for your app: sign-up, sign-in, MFA, social/SAML IdPs, JWTs (ID, access, refresh). Authenticates people to your application.

Identity pool — Cognito federated identities. Exchanges a token for temporary AWS credentials (access key, secret, session token) for an IAM role. Does not store your user passwords.

Permission set — Identity Center’s template for an IAM role deployed into member accounts (PowerUser in Dev, ReadOnly in Prod).

SAML 2.0 federation — your corporate IdP asserts “this employee is Alice”; AWS trusts that assertion and issues a session to a role or to Identity Center.

Cognito user pools versus identity pools

After login, a user pool returns JWTs. API Gateway, AppSync, or an ALB can validate those JWTs. At that point no AWS credential has been issued — the user is signed in to your app, not to S3.

Add an identity pool when the mobile or browser SDK must call AWS APIs directly (for example PutObject to a per-user S3 prefix). The identity pool trusts the user-pool token (or a social/SAML token) and vends temporary credentials for a role you defined. Prefer that over shipping long-term access keys in the app binary.

IAM Identity Center (workforce SSO)

Employees open an access portal, pick an AWS account, and receive a permission-set role. Sessions are temporary. MFA lives at the IdP or in Identity Center. You can use the built-in directory for a small staff, or connect Okta / Microsoft Entra ID / Ping with SAML and SCIM, or use Managed Microsoft AD as the identity source.

Identity Center is not a consumer directory for a mobile game. Older materials say “AWS SSO”; prefer IAM Identity Center on the exam.

SAML federation without Identity Center

You can also federate an IdP directly to IAM roles with SAML (classic pattern: one account, or custom broker). Identity Center is the modern multi-account answer. Either way, humans should not get long-lived IAM user access keys for daily work.

Directory Service — Managed AD vs AD Connector

AWS Managed Microsoft AD — a real Multi-AZ Microsoft Active Directory that AWS operates. Domain join EC2, FSx for Windows, trusts with on-premises forests, Group Policy. Use when you need AD in AWS.

AD Connector — a proxy only. Auth and lookups go to on-premises AD over VPN/Direct Connect. No second writable directory in AWS. If the VPN dies, auth can die with it. Use when identity must stay on-premises.

Simple AD — small Samba-based option; for SAA prefer Managed Microsoft AD unless the stem explicitly wants Simple AD.

Directory Service does not replace Identity Center for multi-account console SSO. Identity Center does not replace Directory Service for Group Policy on FSx.

Use case 1 — mobile app uploads to S3

Need: Millions of customers; email or Google login; upload to s3://bucket/user-id/*; no long-term keys in the app.

Design: Cognito user pool (native + Google) + identity pool + IAM role with a prefix condition on sub. Not IAM users per customer. Not Identity Center.

flowchart LR app[Mobile_app] --> up[User_pool] up --> idp[Identity_pool] idp --> s3[S3_prefix]

Use case 2 — employees, many accounts, Okta

Need: Thirty accounts; PowerUser in sandbox, ReadOnly in prod; MFA in Okta; no IAM users per account.

Design: IAM Identity Center + Okta as external IdP + permission sets assigned by group. Cognito is the wrong product for console SSO.

Use case 3 — domain join without a second AD

Need: Windows EC2 and FSx must use existing on-premises Group Policy; no writable AD replica in AWS; VPN exists.

Design: AD Connector. Use Identity Center separately if console SSO is also required later.

Case study 1 — mobile app writes to S3

Stem

A photo app will have millions of customers who sign in with email or Google. After login, the mobile SDK must upload to s3://bucket/user-id/* without long-term access keys in the binary.

A — wrong Create an IAM user per customer and distribute access keys at sign-up.
B — wrong Put customers into IAM Identity Center and share one permission set.
C — correct Cognito user pool (native + Google), identity pool that trusts it, IAM role allowing s3:PutObject on …/${cognito-identity.amazonaws.com:sub}/*.
D — wrong Public s3:PutObject with a random prefix as security.

Case study 2 — Okta and thirty accounts

Stem

Employees already use Okta. Thirty AWS accounts in an organization. Developers need PowerUser in sandbox and ReadOnly in production. MFA in Okta. No IAM users in each account.

A — wrong Cognito user pool with Okta as SAML IdP; hosted UI opens the AWS console.
B — correct IAM Identity Center, Okta as external IdP, permission sets, assign Okta groups to accounts.
C — wrong AD Connector in every account and access keys in Secrets Manager.
D — wrong One shared IAM user named developers whose key is on a wiki.

Case study 3 — domain join without moving AD

Stem

Windows EC2 and FSx for Windows must apply existing on-premises Group Policy. Identity must stay in the on-premises forest — no second writable directory in AWS. Site-to-Site VPN exists. Directory is not how contractors enter the AWS console.

A — wrong Cognito user pool; join Windows to Cognito.
B — wrong Managed Microsoft AD; migrate all users this weekend; use it for domain join and console SSO.
C — correct AD Connector so domain join and Windows auth proxy to existing AD. Identity Center separately if console SSO is needed later.
D — wrong Identity pool unauthenticated role; skip Group Policy because IAM exists.

Tricky points (still explained simply)

Cognito ≠ Identity Center. Customers vs employees.

User pool ≠ identity pool. JWT for your API vs temporary AWS credentials.

Managed AD ≠ AD Connector. Real directory in AWS vs proxy to on-premises.

SAML proves identity; IAM roles grant AWS power. Federation always ends in a role/session for AWS APIs.

Do not create an IAM user per customer or per daily employee login. Quotas, keys, and no self-service story.
