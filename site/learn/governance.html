Governance — Organizations, Config, CloudFormation, Systems Manager

Must-knowDomain 1 · multi-account guardrails

One AWS account does not scale for a company. Organizations groups accounts and applies SCPs as permission ceilings. Config records what exists and whether it complies. CloudFormation builds infrastructure as code. Systems Manager patches and remotes into instances safely. Together they are how you govern at scale.

Start here — the W questions

Why

Teams want freedom. Security wants “no one turns off CloudTrail” and “no unapproved Regions.” Auditors want proof. Manual clicks in fifty accounts will fail.

What

AWS Organizations + SCPs + consolidated billing. Control Tower for a guided landing zone. Config for inventory and rules. CloudFormation / StackSets for IaC. Systems Manager (Session Manager, Patch Manager, Parameter Store). Service Catalog for approved products.

Where

Organizations is global across your estate. Config recorders and CloudFormation stacks are Regional (StackSets fan out). SSM manages instances wherever they run (including hybrid).

Which pieces matter

SCP deny vs IAM allow · management account exception · Config rules · StackSets · Session Manager (no SSH bastion) · Parameter Store vs Secrets Manager. Those dominate SAA governance stems.

Core knowledge (beginner foundations)

SCPs are guardrails, not grants

A Service Control Policy sets the maximum permissions for member accounts and OUs. It never grants access by itself. IAM still must allow the action. SCPs do not restrict the management (payer) account the same way — a classic exam fact.

OU (organizational unit) — folder of accounts (Prod, Sandbox, Security).

Control Tower — automated landing zone with preventive (SCP) and detective (Config) guardrails plus Account Factory.

Config rule — continuous check (for example “S3 buckets must be encrypted”). Can flag or trigger remediation.

Stack / StackSet — one template’s resources; StackSet deploys across accounts/Regions.

How multi-account guardrails stack

flowchart TD root[Organization_root] --> ou[OUs] ou --> acct[Member_accounts] scp[SCPs] --> ou scp --> acct iam[IAM_policies] --> user[Users_roles_in_account] cfg[Config_rules] --> acct

SCP + IAM evaluation idea from Service control policies (SCPs). Both must allow.

CloudFormation and Systems Manager

CloudFormation is declarative IaC (YAML/JSON). Change sets preview updates; drift detection finds manual edits. Prefer it (or CDK that synthesizes it) when the stem wants repeatable infrastructure.

Session Manager gives shell access through IAM and SSM Agent — no inbound SSH, no bastion host required. Patch Manager baselines OS patches. Parameter Store holds config (Secrets Manager when rotation/dynamic secrets dominate).

Remember “Deny a service org-wide” → SCP. “Who can call APIs day to day” → IAM. “Is this bucket still public?” → Config. “SSH without opening port 22” → Session Manager.

Use case 1 — block risky Regions

Need: Member accounts must not launch resources outside approved Regions.

Design: SCP deny on non-approved Regions attached to OUs. IAM alone is not enough if admins can widen IAM.

Use case 2 — compliant inventory

Need: Continuously detect unencrypted EBS volumes and alert.

Design: AWS Config managed rule + SNS/EventBridge. Optional automatic remediation document.

Use case 3 — same baseline in 30 accounts

Need: Deploy a security IAM role and Config recorder everywhere.

Design: CloudFormation StackSets from the delegated admin/management account.

Case study 1 — SCP vs IAM

Stem

Security must ensure no member account can disable CloudTrail, even if an account admin is AdministratorAccess.

A — wrong Ask every admin to promise not to.
B — correct SCP that denies cloudtrail:StopLogging / delete trail actions on member OUs.
C — wrong Only a Config rule — detects after the fact unless combined with prevention.
D — wrong SCP on the management account expecting it to behave like member accounts.

Case study 2 — Config vs CloudTrail

Stem

You must list every security group that allows 0.0.0.0/0 on port 22 right now and alert on new ones.

A — wrong CloudTrail alone — great for who changed it, weak as continuous inventory query.
B — correct AWS Config rules on restricted SSH, SNS on NON_COMPLIANT.
C — wrong Only Cost Explorer.
D — wrong SCP that grants Detective.

Case study 3 — Session Manager

Stem

Operators need interactive shells on private EC2. No inbound SSH from the internet. Audit who did what.

A — wrong Public bastion with wide SSH.
B — correct SSM Session Manager + instance profile + CloudTrail/Session logging.
C — wrong Disable all access forever.
D — wrong Put SSH keys in a public S3 bucket.

Tricky points (still explained simply)

SCP + IAM both required. Allow in IAM but deny in SCP → denied. Allow in SCP but no IAM → denied.

Config ≠ CloudTrail. Config = “what is the resource state / compliance.” CloudTrail = “which API call happened.”

Parameter Store vs Secrets Manager. Config values and simple secrets → Parameter Store (Advanced/standard tiers). Automatic rotation and external secret engines → Secrets Manager (also fine for many secrets stems).

Trusted Advisor / Compute Optimizer — advisory checks; not a replacement for SCPs.
