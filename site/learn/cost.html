Learn / Cost

Cost optimization — pay for what you need, commit when steady

Must-knowDomain 4 · Savings Plans, Spot, data transfer

Domain 4 is less about clever math and more about matching workload shape to pricing. Steady 24×7 compute → commit (Savings Plans / RI). Spiky batch that can die → Spot. Wrong architecture (NAT, cross-AZ chatty apps, public egress) often costs more than the instance type.

Start here — the W questions

Why

On-Demand is flexible and expensive at scale. Leaving oversized instances, idle load balancers, and chatty cross-AZ traffic on forever burns budget without helping users.

What

EC2/Fargate/Lambda purchasing options, S3 storage classes and lifecycle, data-transfer awareness, and tooling: Cost Explorer, Budgets, Cost Anomaly Detection, Compute Optimizer, Trusted Advisor.

Where

Pricing is Regional (and sometimes AZ-sensitive for data transfer). Consolidated billing rolls cost to the Organizations payer account.

Which pieces matter

On-Demand · Savings Plans · Reserved Instances · Spot · S3 tiers · data transfer / NAT · right-sizing tools. Those cover most Domain 4 stems.

Core knowledge (beginner foundations)

Match commitment to interruptibility

If the work must keep running and looks steady, buy a commitment. If the work can checkpoint and retry, use Spot (up to ~90% off, reclaimed with short notice). If you are still experimenting, stay On-Demand.

Watch data transfer: internet egress, NAT Gateway processing/bytes, cross-AZ traffic for chatty tiers, and cross-Region replication. Sometimes a gateway VPC endpoint for S3 beats NAT egress.

Remember Savings Plans do not reserve capacity. Spot is wrong for stateful single-node databases. “Cheapest S3 for rarely opened backups” → Glacier classes via lifecycle, not all-Standard forever.

Use case 1 — steady web fleet

Need: ASG runs all year; instance sizes may change.

Design: Compute Savings Plans covering the baseline; On-Demand/Spot for burst if the app allows.

Use case 2 — nightly analytics

Need: EMR/Spark jobs that can retry; cost sensitive.

Design: Spot for task nodes (diversified pools); On-Demand or reserved for critical master/core if required.

Use case 3 — budget guardrails

Need: Alert before the bill surprises finance.

Design: AWS Budgets + Cost Anomaly Detection; tag allocation; Cost Explorer reports. Optional SCP to block expensive unused Regions.

Case study 1 — flexible commitment

Stem

Steady compute spend across EC2, Fargate, and Lambda. Instance families change quarterly. Maximize discount with flexibility.

A — wrong Standard RI locked to one family forever.
B — correct Compute Savings Plans.
C — wrong All Spot for the payment database.
D — wrong Dedicated Hosts for every microservice.

Case study 2 — Spot fitness

Stem

Image-processing workers pull jobs from SQS, are stateless, and can retry. Cut cost aggressively.

A — correct Spot (or mixed instances ASG) workers + SQS.
B — wrong Spot for a single-node RDS primary.
C — wrong Only On-Demand with no SQS buffer.
D — wrong Snowball Edge as compute.

Case study 3 — S3 lifecycle

Stem

Compliance keeps objects seven years; after 90 days almost never read. Minimize storage cost.

A — wrong Keep everything in S3 Standard.
B — correct Lifecycle to IA/Glacier Deep Archive (per access pattern) with retrieval time that still meets RTO.
C — wrong Delete at day 91 when retention is seven years.
D — wrong Store only on instance store disks.

Tricky points (still explained simply)

RI Marketplace and Convertible quirks still appear; prefer Savings Plans language on modern stems when flexibility is stressed.

Spot interruption is normal — design for it (SQS, checkpoint, diversified pools).

Egress is architecture. CloudFront can reduce origin egress cost for public content; endpoints can reduce NAT cost for S3.

Trusted Advisor / Cost Optimizer suggest; they do not auto-buy commitments without you.
