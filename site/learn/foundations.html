AWS foundations — Regions, AZs, and who owns security

Must-knowAll domains · start here

AWS is a huge platform, but three ideas unlock almost every exam question: who is responsible for a control, where a resource lives, and whether you need high availability inside one Region or disaster recovery across Regions. Learn these first. Later chapters become easier.

Start here — the W questions

Why

You need to know: “Is this my job or AWS’s?” and “If this building dies, does my app die?” Without that, every product name feels random.

What

AWS is a global cloud built from Regions (geographic areas), Availability Zones (independent data centers inside a Region), and edge locations (points of presence for DNS, CDN, and similar). The shared responsibility model splits security between AWS and you.

Where

Your data stays in the Region you choose unless you turn on replication. Multi-AZ keeps you up if one AZ fails. Multi-Region keeps you up if a whole Region fails. Edge services sit outside your VPC, closer to users.

Which pieces matter

Shared responsibility · Region · AZ · edge · Multi-AZ (HA) vs Multi-Region (DR) · account as blast-radius boundary. Those six ideas appear everywhere on SAA-C03.

Core knowledge (beginner foundations)

Shared responsibility in one breath

AWS is responsible for security of the cloud: buildings, power, network cables, hypervisors, and the managed software AWS runs. You are responsible for security in the cloud: your data, who can sign in, encryption choices, network rules (security groups), guest OS on EC2, and application code. “Managed” never means “AWS chose my encryption key and my security group.”

Region — a geographic area AWS isolates from other Regions. Pick one for latency to users, for data-residency law (“must stay in the EU”), and for which services exist there. Data does not leave a Region unless you configure a copy (S3 Cross-Region Replication, RDS read replica, and so on).

Availability Zone (AZ) — one or more discrete data centers with independent power and networking, linked to other AZs in the same Region by fast private fiber. Spreading work across AZs is high availability (HA) inside one Region. It is not protection if the whole Region fails.

Edge location — a point of presence for services such as CloudFront, Route 53, and WAF. You do not launch EC2 “in an edge.” You cache or terminate traffic there.

Account — the hard isolation boundary. Resources in Account A are invisible to Account B until you write a trust, a resource policy, or a share. Prefer separate accounts for prod, test, and sandbox.

How AWS draws the shared-responsibility line (from AWS docs)

AWS publishes a simple split: security of the cloud versus security in the cloud. The more managed the service, the more AWS does — but you always keep data, identity, and configuration.

Global infrastructure — Region, AZ, edge

AWS documents Regions as isolated geographies and AZs as independent failure domains inside a Region. Edge locations sit closer to users for DNS and content delivery.

flowchart TB users[Users] --> edge[Edge_CloudFront_Route53] edge --> r1[Region_A] edge --> r2[Region_B] r1 --> az1[AZ_1] r1 --> az2[AZ_2] r1 --> az3[AZ_3] r2 --> azb[AZ_1_in_B]

Matches the hierarchy in Regions and Availability Zones and Global infrastructure.

Local Zones put compute near a metro for very low latency. Wavelength puts compute inside a 5G carrier network. Outposts puts AWS racks in your data center. Know the names; SAA rarely asks you to size them.

Scope of a service: global, regional, AZ

IAM users and roles are global identities (you do not create “a role in eu-west-1”). Route 53 public zones and CloudFront are also global control planes. Most resources are regional: VPC, S3 data, KMS key, RDS, Lambda. Subnets and EBS volumes are AZ-scoped — you cannot attach an EBS volume in AZ-a to an instance in AZ-b without a snapshot and a new volume.

High availability versus disaster recovery

Multi-AZ is HA. It survives loss of one data center. Examples: RDS Multi-AZ, an ALB across three subnets, an Auto Scaling group in two AZs.

Multi-Region is DR (or active-active). It survives loss of a whole Region. AWS names strategies such as backup/restore, pilot light, warm standby, and active-active. Do not pick “add a second AZ” when the stem says “Region failure.”

Availability is “can a client reach a healthy copy right now.” Durability is “are the bits still stored after a long time.” S3’s famous “eleven nines” are durability, not the same as availability.

Use case 1 — pick a Region for law and latency

Need: Customers are in Tokyo. Personal data must stay in Japan.

Design: Run the stack in an Asia Pacific Region that meets residency (for example ap-northeast-1). Do not “fix latency with a US Region and hope.” Edge (CloudFront) can cache public content worldwide; the origin and database stay in the residency Region.

flowchart LR user[User_in_Tokyo] --> edge[CloudFront_edge] edge --> origin[App_in_ap_northeast_1] origin --> db[RDS_same_Region]

Use case 2 — survive one AZ, plan for Region loss

Need: Minutes of downtime if one data center fails. Hours of recovery if the whole Region fails.

Design: Multi-AZ compute and database for HA. Cross-Region snapshots or a read replica / Backup plan for DR. Those are two different designs.

flowchart LR alb[ALB] --> asg[ASG_two_AZs] asg --> rds[RDS_MultiAZ] rds --> snap[Snapshot_copy_to_DR_Region]

Case study 1 — who encrypts the managed database

Stem

A company moves PCI MySQL from EC2 to Amazon RDS. Compliance still needs encryption at rest, TLS, and private subnets. An architect says: “RDS is managed, so AWS owns encryption and network isolation.” Who is right?

A — wrong Agree. Managed means AWS owns encryption and security groups.
B — correct Disagree. AWS patches the host and runs Multi-AZ storage. You still enable KMS, force TLS, and use private subnets with a tight security group.
C — wrong Disagree only about TLS; encryption at rest is always on and cannot be configured.
D — wrong Move to DynamoDB because NoSQL has no customer security work.

Managed infrastructure is not a transfer of data-classification duty. See the shared responsibility model.

Case study 2 — AZ outage versus Region outage

Stem

The app is in us-east-1: Auto Scaling in one subnet, single-AZ RDS. Leadership wants minutes of recovery if one data center fails, and a plan if the whole Region fails with an RTO of hours. What addresses both?

A — wrong Enable RDS Multi-AZ only — AWS will fail the instance into another Region automatically.
B — wrong Add web servers in Europe; leave the only database in one AZ in us-east-1.
C — correct Spread the ASG across two or more AZs behind an ALB and use RDS Multi-AZ for the data-center goal. For Region failure, use snapshot copy / cross-Region replica / AWS Backup and a restore plan.
D — wrong Put the database on RAID-0 EBS in one AZ so disks cannot fail.

Case study 3 — private path to S3 without NAT

Stem

Private EC2 instances must read and write an S3 data-lake bucket in the same Region. They must not use the public internet. Security forbids a NAT Gateway for cost and path reasons. Lowest cost?

A — wrong Add a NAT Gateway and call the public S3 endpoint over TLS.
B — correct Create a gateway VPC endpoint for S3, attach it to private route tables, and limit the bucket policy to that endpoint.
C — wrong Use an interface endpoint for S3 plus a NAT “for defense in depth.”
D — wrong Copy the lake onto EBS volumes on every instance.

Tricky points (still explained simply)

“Managed” ≠ “no customer security.” You still own IAM, encryption toggles, and network rules on RDS, Lambda, and S3.

Multi-AZ ≠ Multi-Region. Multi-AZ is HA. Region failure needs a second Region.

Edge ≠ AZ. You cannot run RDS in an edge location.

Cost is last among equals. Functional fit, security, and resilience beat a cheap single-AZ design when the stem required HA.

Light touch on the exam Exact AZ counts per Region, Local Zone city lists, Wavelength carriers. Know the failure domain: AZ vs Region vs edge.
